# futatabi — 投稿前ゲート停止位置の再調査（2026-11-22）

**結論：投稿UIの送信操作は成立し、モーダルが閉じるが、HTTP POSTを発行する段階に到達した証拠はない。送信停止の具体的な分岐条件は未特定。Dart AOT解析へは進まず停止する。**

対象は素のふたったー3.1.1、`com.Nanasaki.ftutter`、Androidエミュレータ `emulator-5554`。実サイトへの投稿・実認証・パッチコード改変はなし。

## 同一経路での確認

エミュレータの既存`flutter.itaList`に直接登録済みの`http://127.0.0.1:18766/aimoge/`を使用。`adb reverse --list`で`tcp:18766 tcp:18766`を確認。サーバーは外部サイトへ転送しないテスト専用観測プロセス。カタログ・スレは[先行実証のmay実物HTML](gate4-may-real-html-parser-20261122.md)をローカルで再生した（第三者HTMLは非公開の作業領域）。

- 同じ素のアプリから`GET /aimoge/futaba.php?mode=cat`、`GET /aimoge/res/1449110872.htm`が届き、カタログとスレ画面まで到達。したがって少なくとも**GETの通信不通ではない**。
- 純正スレUI→鉛筆アイコン→投稿フォームでコメント入力→送信ボタン操作。送信後、フォームは閉じた。**POST受信0件**。
- 純正カタログUI→鉛筆アイコン→題名／本文が入力済みの新規スレフォーム→送信ボタン操作。送信後、フォームは閉じた。**POST受信0件**。
- `POST`が来た場合はHTTP 403を返す観測サーバーだが、実際にその応答をアプリが処理する機会はなかった。**成功／失敗判定（200、302、403、本文、Cookieなど）未実証**。
- 純正UIに「投稿成功」とみなせる新規レス／スレは表示されず、元の画面に戻っただけ。「フォームが閉じた＝成功」とは判定しない。

## 仮説(a)：guid=onが必須なのか

フィクスチャへ`GET /aimoge/futaba.php?guid=on`の応答（HTTP 200、ローカルテスト用`Set-Cookie: test_guid_fixture=1`）を追加。Windows上の**手動GET 1件**で応答を検証した。

その後、同じボードの新規スレフォームから送信したが、**アプリからguid=onのGETは0件、POSTも0件**。手動GETで得たCookieは端末側には渡していない。

**結論：guid=onが送信前に自動要求される経路は今回の実行では観測されなかった**。ただし、アプリが事前に他所でCookieを必要とする場合や、Cookieが不足した段階より手前で送信が中断した場合は排除できない。「Cookie不足が原因」とも「Cookie不要」とも断言しない。

## 仮説(b)：板URLのドメイン／形式の判定か

既存の登録UIからローカル板を追加できない問題は[過去の変数分離実験](gate4-variable-experiments-20261122.md)で検証済み。今回は保存先に直接登録した板から、同じURLで**GETが成立するにもかかわらずPOSTが到達しない**ことを再確認した。

既知の`may.2chan.net`ドメイン板へ実際に投稿すると「実サイト送信禁止」に抵触するため実施しなかった。実際の既知ドメインを完全にローカルへ置換するホスト／TLS介入も、この限定調査では実施しなかった。

**結論：既知ドメイン照合の可能性は残るが、今回の実測だけで肯定・否定はできない**。実投稿無しの通信遮断条件下で同条件を比較するには、MUSEが改めて隔離方法を判断する必要がある。

## MUSEへ引き継ぐ判断材料

- `resto`の多数の文字列、`kakikomiSucceedWithThisCokkieProvider`、`futaba.php?guid=on`はMUSEがlibappから確認した有力な**静的手掛かり**。しかし送信処理への分岐対応は今回のlogcatとHTTPアクセス記録から確定できなかった。
- 前回の[投稿下書き保存実証](write-login-feasibility-20261122.md)により、`kakikomiData`は題名／名前／メール／本文／添付パスの入力状態を保持すると強く支持される。**送信完了や投稿成功を表すものではない**。
- フォームの送信ボタンで画面が戻るため、入力側の操作自体は進行している。ただし**送信処理を行わないドメイン判定**と**Dart側で握り潰した例外／応答**は、観測だけでは区別できない。
- **次工程の選択はMUSE判断**：既知ドメインをローカルへ安全に隔離して純正送信ゲートを比較するか、Dart AOTの投稿箇所だけを解析するか、別UIへ切り替えるか。今回ここから先へは進まない。

## MUSE確定設計（今後の前提として記録）

- **あいもげ**：公式アプリ承認`PKCE S256`方式を採用。資格情報は端末内のアプリ専用領域にだけ保存し、`FlutterSharedPreferences`の`kakikomiData`等へ保存しない。再認証は利用者の操作が必要。
- **めぶき**：上記は当時の判断。2026-11-22に所有者申告の管理人許可を前提としてMUSEが**GO**へ変更済み。詳細は[追加技術調査](mebuki-auth-api-research-20261122.md)。
- **投稿成功／失敗**：ふたったーが実際に成功と判定する条件を調べ、成功したと偽装するHTTP応答を作らない。POSTが来ない現状では判定未確定。

今回の検証は**実サイトへの投稿、トークン発行、OAuthログイン、アプリ改変、公開リリースのいずれも実施していない**。一時観測サーバーは元の18766番フィクスチャへ復旧して終了。

## 追加調査：Android側全通信キャプチャ（2026-11-22、MUSE追加指示）

**方法**：root可能な`emulator-5554`で`tcpdump 4.99.4 -i any -nn -s 96 -w <pcap>`を実行。全インターフェースのパケットを記録し、`tcpdump -nn -tttt -r`で後から宛先とTCP SYNを照合。PCAPの先頭96バイトのみ保存し、全HTTP本文や個人情報の蓄積を避けた。調査対象は素の`com.Nanasaki.ftutter`（UID **10218**）。

**安全策**：予期せず実サイトに投稿しないよう、AndroidのOUTPUTチェーンにUID 10218だけを対象とするIPv4外部宛`REJECT`（127.0.0.0/8以外）とIPv6外部宛`REJECT`（::1以外）を設置。ローカルの`adb reverse tcp:18766 tcp:18766`は許可。各観測の前後に両規則の`pkts`カウンターを読み取り、最後に**両規則を完全に削除**した。他アプリには適用していない。

| 観測窓 | tcpdumpの結果 | 確認した宛先・ポート | 外部宛遮断カウンター |
| --- | --- | --- | --- |
| カタログ表示（既存のmay実物HTMLを18766のローカルリプレイから取得） | **19パケット**、TCP接続2本、PCAP 1,824 bytes | **127.0.0.1:18766**、送信元ポート35370・35386 | IPv4 **57→57**、IPv6 **68→68**（増分0） |
| 素のふたったーのスレでコメントを入力して「書き込む」を押した瞬間とその後 | **1パケット**、TCP SYN **0件**、PCAP 136 bytes | 端末の`fe80::2 → ff02::1` ICMPv6ルーター通知のみ。**アプリのTCP宛先は観測されず** | IPv4 **57→57**、IPv6 **68→68**（増分0） |

カタログ時は元アプリ自身の`Ftutter/3.1.1` UAによる`GET /aimoge/futaba.php?mode=cat`と対応するローカル接続を確認。既存スレ`No.1449110872`も既存UIで表示できた。カタログには画像要因由来のnull-check警告が出たが、スレを開く操作は実行可能だった。投稿ではフォームが閉じてスレ画面に戻ったものの、リプレイサーバーへのPOSTも、新規の外部宛て接続も確認できなかった。

**観測の限界**：`tcpdump`は全UIDの端末通信を含むため、ルーター通知はアプリ通信ではない。OUTPUTで拒否された通信はtcpdumpに出ない可能性があるので、**UID単位の遮断カウンターも独立に照合**した。パケットを送る前のアプリ内検証、実際に接続しようとした可能性のあるホスト名、キャッシュや内部的な例外の有無までは判定不能。カウンター増分0は**この観測窓に、UID 10218が外部宛てIPパケットを発行したことを示す証拠がない**という意味であり、「既知ドメイン照合が原因」との断定ではない。

**証拠**：[パケット数・宛先・ハッシュ・遮断カウンター・復旧状態の集計](gate-evidence/post-submit-tcpdump-20261122.json)。生PCAPはPCのGit管理対象外`apk-inspection/netgate/`に保持：

- `baseline-valid.pcap` 1,824 bytes / SHA-256 `0d3594ece6c5060a758f3e1afce48da6dcd7f50a2cbda64c43da6acdd662b0a1`
- `post-only.pcap` 136 bytes / SHA-256 `cab022822a4fcf3666458a6e0e3a33b2bd40e132c216466d25a185b766762d7a`

**終了状態**：tcpdump停止、iptables/ip6tablesの追加ルール削除を読み戻し確認。18766は元の`tests/adb_reverse_fixture.py --port 18766`に復旧、adb reverseは保持。元アプリ／Bridge・パッチ・Releaseはいずれも変更なし。MUSEのDart AOT解析と照合するため、接続先の特定と送信処理の原因判断はここで停止する。
