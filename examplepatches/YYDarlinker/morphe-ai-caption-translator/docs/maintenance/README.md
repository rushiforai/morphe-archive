## 一张卡的执行与交接

1. 读取根AGENTS、当前状态/最新记录、任务卡和相关路线。核对分支/HEAD、入场脏树/未跟踪/删除状态并保存原件和哈希；用入场字节判定本轮改动。
2. 在卡内持续完成授权工作包，按实际机制做针对性回归；固定工程输入后完成一次必要完整验证。脚本接口/失败码有实质变化才增加必要工具合同，不以测试数量代替行为证据。
3. 将同次XML、receipt、compiled ZIP/输入指纹绑定封存后再运行后续Gradle。正常构建可管理中间输出；保护源码、发布/候选交付、封存日志/报告/回退原件，不反复累加可再生成class清单，不改44恢复历史。
4. 结果写 `docs/maintenance/results/<task-id>-RESULT.md`，证据放E: `validation/runs/`，产物使用独占目录。报告实际命令/退出码、两组counts、包与组合输入哈希、范围外保护、未验项及逐文件回退；不拿HEAD总diff、旧报告或缺文件替代本次结果。
5. 回退默认只检查退出哈希；实际dry-run、后续编辑整批拒绝，状态/镜像成对。保留结果/证据/历史归档和全部包；不reset/clean、覆盖未来改动或清用户数据。
6. 执行只标“完成待复核”，统筹保持“待复核”。统筹按实际diff/日志独立决定接受、补正或暂缓及下一任务；不无理由重复全套。用户新授权优先，但维护不自动授权发布、外发、设备安装或真实付费调用。

用户转交摘要使用中文并给绝对路径，包含任务/结论、结果/证据、实际修改、两模块counts和负向、产物身份/哈希、保护/镜像、未验输入、回退及待统筹判断。详细证据留在本机可检查文件，不只藏在聊天进度中。
