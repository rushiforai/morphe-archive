## 4. 必须解决的问题

### A. 当前有效入口与环境

选择并整理一个当前常用验证入口，复用有效的 `.devenv` 环境和已有工具。日常单测入口可保留，完整验证入口应有清楚的调用关系；旧的固定 v1.5.4 验证必须被明确限定为历史用途或安全更新，不能继续作为当前默认说明。

默认不做真实模型 API 测试，不因机器里存在密钥而调用模型。进程临时目录、Gradle home 和 Android user home 遵守 AGENTS。本地入口可有 Windows wrapper，CI 共用的检查逻辑应避免依赖 Windows 绝对路径。

### B. 两组测试与报告有效性

明确执行 `:translation-core:testDebugUnitTest` 和 `:extensions:extension:testDebugUnitTest`；保留本地化和源码/来源边界检查。对每模块输出真实 tests/failures/errors/skipped 和报告路径，任一必需模块缺失、零测试或失败不得整体通过。

报告必须与本次源码/构建有关。允许构建系统基于输入确认的有效复用，不能仅扫描旧 XML 就宣称本轮测试通过。至少完成一次经新入口确认两组测试有效的实际运行；必要时只对相关任务强制重跑。699 是基线参考，不是硬编码通过条件。

### C. 指定本次候选，区分候选与正式发布

构建当前 MPP，复制/保存到本轮独占候选目录。包检查接受显式包路径、期望版本/build ID 或等价候选清单，不能只找“最新 MPP”、固定旧版本或任意目录中相同文件名。

候选校验与正式 release 校验分开：候选允许 local build ID，正式发布仍拒绝 local 标识。不要通过关闭 release 约束来放行候选。已有正式校验调用应保持有效；需要改参数时同步修改所有有效调用处并验证拒绝路径。

核对 MPP、必要 DEX/资源、内嵌与本次独立 MPE 一致性、版本/build ID、来源和泄漏检查。测试产物/测试 harness 不混入交付。检查报告列明数据来源，不能拿另一次独立 MPE 与当前包碰巧相等当作构建关联的全部依据。

本次清单至少记录：分支、HEAD、工作树指纹/清单、运行 ID、工具版本、实际命令及退出码、每模块测试结果、指定包与独立 MPE 路径/哈希、检查结果及未覆盖项。指纹应定义范围，候选构建所用源码与最终报告一致；若测试后改变相关实现，补跑受影响检查。

### D. CI 与发布前检查接线

补齐 `.github/workflows/validate.yml` 和 `.releaserc` prepare 中的 core 测试；检查 `release.yml` 的其他测试入口是否也需一致更新。发布前运行，不能依靠已发布后的测试补救。

CI 触发覆盖本项目采用的 dev/codex 开发方式和相应 PR；不要求为不相关分支无限扩展。修正 core/extension 测试报告和候选包上传路径，保证失败时必要证据可归档。

候选验证不能强迫仍在线的 1.5.7 元数据变成 1.5.8。拆清当前候选一致性、已发布元数据内部一致性和真正发布时的一致性。保留 semantic-release 为唯一发布者，不新造发布流程。

本地可验证工作流/配置及被调用脚本，但没有实际远端运行时必须明确“远端 CI 未运行”；不能把静态检查描述为 GitHub 验证已通过。

### E. 有意义的拒绝路径

使用临时 fixture/副本，至少证明以下结果；保护真实包和真实测试报告，不直接破坏它们来制造故障：

1. 必需模块缺报告或零测试 → 不通过。
2. 单测/构建子命令失败 → 失败被保留，不继续报整体成功。
3. 传入期望身份不匹配或明显属于另一轮的候选 → 不通过；多个旧包存在时仍只检查指定输入。
4. 候选 local build ID 在候选模式可验证，在正式 release 模式仍被拒绝。

不要求新增与这些目标无关的大型测试框架。使用项目已有工具即可。未具备 APK/官方包时，组合验证状态为“未执行/缺输入”；源码和候选检查若已完成，应能如实单独报告。
