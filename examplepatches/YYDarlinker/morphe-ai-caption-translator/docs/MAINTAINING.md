# Maintaining the independent bundle

集中工程治理和分页简化实验已经收尾。日常优化由可复现缺陷、实际功能需求、测量到的瓶颈或明确维护障碍驱动；减少行数不作为独立任务。新功能另开普通分支，与当前缺陷修复候选隔离；具体身份及手机验收状态见PROJECT-STATE。

Start with [project state](PROJECT-STATE.md), [development](DEVELOPMENT.md) and the relevant part of [architecture](ARCHITECTURE.md). State owns current package identity, known issues and pending external work. A maintainer does not need to read old task cards or chat histories.

## Make a bounded change

1. Record branch/HEAD and existing worktree changes. Save originals for files being changed; do not attribute previous work to the new task.
2. Follow the source boundary: patch bindings → extension host/adapters → core, with UI using application ports. Check dynamic patch calls, Android XML constructors and generated resources before declaring a symbol unused.
3. Use the daily entry for affected behavior. Test normal output and the relevant rejection/failure path. Keep meaningful assertions and real fixtures; do not replace an expected result with output generated by the implementation being tested.
4. For a final candidate, use a unique local build ID and run the canonical full entry once against fixed inputs. It binds both suites, rebuilt test classes, exact MPP/MPE/UI artifacts and source fingerprint. A test count alone is not quality evidence.
5. Resource/Hook/DEX changes and final product delivery also need finite composition inputs. Use `:patches:verifyComposition` then `:patches:auditComposition`; see [compatibility](COMPATIBILITY.md). Unit tests and resource compilation do not establish phone behavior or model translation completeness.
6. Record actual results and unverified boundaries under `validation/runs/<run-id>/`. Update state and its mirror together. Source delivery, device observation and publication are distinct; see [releasing](RELEASING.md).

Keep the incremental daily loop. Full verification deliberately rebuilds Java test destinations to reject deleted-test bytecode. Do not repeat full builds merely because a review moves to another chat.

## Maintain tests by failure detection

- Name the user behaviour or contract a test protects and where its expected result comes from. A captured subtitle, fixed Unicode cluster, signed URL or failed-cache case is worth retaining when it detects a meaningful error; specificity alone is not redundancy.
- Exercise the project entry point. Constructing a generic Android widget and filling in the expected attributes does not verify the addon that configures it. Keep source/ABI/resource checks for declarations that are themselves contracts; prefer actual execution for behaviour.
- Remove a weaker duplicate only after identifying the retained stronger assertions and the setup differences. Use a small controlled fault or real historical failure when equivalence is uncertain. Equal coverage or one shared failing mutant does not prove universal redundancy.
- Keep one current specification for generated data. Runtime localization checks compare the input catalog with compiled XML and lookup; golden export fixtures pin observable text, with common raw output stored once. Regeneration writes a proposal and fails until reviewed.
- Separate measurements and evidence exports from assertions. Ordinary tests need not write historical screenshot/JSON ledgers. SDK matrices belong where platform behaviour matters; a zero-call live run and a stale compiled class never count as successful validation.

Stop test governance after confirmed low-value assets are removed, changed contracts have relevant evidence, the ordinary checks pass and production inputs remain protected. Do not add a test framework, permanent fault-injection service or another recurring audit solely for this review.

## What is enough to maintain

| Requirement | Practical criterion |
| --- | --- |
| Understandable structure | One state page, working documented commands, a source responsibility map and contracts for risky boundaries |
| Product protection | Native CC/target ownership; zero model requests in source mode; no source-text fallback on translation failure; stale sessions cannot gain display/request authority |
| Bounded work | Attempt/repair/retirement gates and provider waiting honored; cache/configuration failures do not fabricate success or expose credentials |
| Useful verification | Reproducible source-to-package identity, relevant behavioral regressions, package boundaries and finite composition/phone observations when affected |
| Controlled assets | Dependencies/fixtures/licences have consumers; generated output is ignored; unique evidence and release bytes are recoverable; historical reports are not build prerequisites |
| Honest delivery | Local improvements are not remote changes; a local candidate is not a published release or accepted phone build |

When these hold, return to ordinary feature/defect work. File lengths, naming preferences, splitting another helper, removing a handful of lines or adding acceptance documents are not reasons to launch another repository-wide program. A reproducible functional defect remains actionable when housekeeping is complete.

## Evidence, retention and rollback

- Public source includes code, useful tests/fixtures, localization inputs and checked generated resources, canonical tools, build/release configuration, locks, licences and provenance. Required build knowledge must not depend on private reports.
- Git tags/commits and Releases retain committed history. Superseded plans, prompts and stage reports belong in one indexed private recovery archive when unique bytes matter; see [history](history/README.md). Do not retain active copies solely because a prior AI produced them.
- Keep diagnostics private. Preserve release/rollback MPP/MPE/APK bytes, same-run XML, receipts, input/artifact identities and evidence for unresolved defects. An original failure must remain distinguishable from a later pass.
- `.tmp/`, compiler output and completed Robolectric native extraction are regenerable. Check active workers and unique inputs before removing them. Keep installed toolchains and shared dependency caches. Do not copy large generated evidence trees into every source snapshot.
- Roll back only actual task changes after checking current bytes against recorded exit hashes. Refuse to overwrite later edits. Preserve result/evidence and release packages; do not use a repository-wide reset.

The objective remains a functional, reliable, restrained independent package. It does not require an official Morphe PR, perfect code, a universal device matrix or another planned restructuring round.
