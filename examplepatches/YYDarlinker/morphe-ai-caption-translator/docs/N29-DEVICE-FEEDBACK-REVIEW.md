## 2. 两个确定的 UI 缺陷

### 播放器菜单“路”

源码 `CaptionQuickToggle.java` 直接拼接：`CaptionStrings.settings(a,"ai_title") + " 路 " + CaptionStrings.settings(a, ... ? "on" : "off")`。截图中的“路”因此是硬编码字符，和官方1.45、字体、Morphe排序无关。

N30 删除硬编码文本，改为一个完整的资源化菜单标签，例如 `cap_ai_quick_toggle_on` / `cap_ai_quick_toggle_off`，或一个合法的格式化资源。由应用语言资源决定分隔方式，不允许在Java中拼接中文字符。14种语言必须有资源，英文技术字段不应混入播放器可见标签；运行时验证开/关各一遍。

### AI设置入口 summary

`DeepSeekCaptionResourcePatch.buildPreferenceScreen()` 当前把 AI 页面 summary 设为 `@string/cap_autosave`，而 `cap_autosave` 的中文值是“修改后自动保存”。这解释了截图中的错误说明。N30新增专用 `cap_ai_summary`，描述功能本身，例如“使用你配置的 AI 服务实时翻译视频字幕”，并为14种应用语言提供对应文案。自动保存说明只保留在确实涉及自动保存的输入项，不能继续作为 AI 页面 summary。

## 3. 等待延长和连接失败

诊断出现三次 `REBUILD_HTTP_FAILURE`，均为 `SocketException`：中文会话20约2.6秒，中文会话23约0.6秒和1.1秒。成功请求的网络 RTT 多次达到4–8秒，最高约10.16秒；焦点请求自身也有9.52秒和6.12秒。因此不能把全部等待归因于分页或UI，远程连接实况确实恶化。

N29新增的 `!everReady` 邻块 bootstrap 允许焦点块尚未接纳时就提交邻块远程请求。它在离线固定回放中把边界等待从2029ms降为0，但在真机网络不稳定时会提前占用供应商连接和本地请求资源。当前诊断没有429，但有SocketException和长RTT，足以说明“更早发更多请求”不是稳妥的默认策略。

N30将启动策略改为：首个焦点请求未成功接纳前，邻块只做内存/磁盘 cache 检查，不发远程翻译；首个焦点成功后才恢复已有prefetch2/总4规则。这样会放弃N29在理想固定回放中的部分零等待收益，但降低网络拥塞、连接失效和失败后连续“翻译中”的风险。不能通过隐藏等待文字、延长字幕持有时间或无限重试来伪装改善。

失败处理还应记录连接阶段和剩余deadline；同一块的有限重试仍受现有attempt/repair上限约束，SocketException不能把字幕永久留在pending状态。失败应沿既有安全空白/明确诊断路径收敛，不能导致旧请求或旧Session重新取得显示权。

## 4. 视频详情页、悬浮窗、全屏切换卡顿

诊断中出现：

- `PLAYER_TRANSITION_CAPTION_GUARD` 6次，`PLAYER_TRANSITION_STABLE`仅3次；每次稳定恢复要观察若干帧。
- `NATIVE_RENDERER_VIEW_NOT_FOUND` 41次、`NATIVE_RENDERER_VIEW_TREE` 498条。树摘要来自主线程有界遍历，当前扫描最多1200个View，并在未找到时生成最长约16KB摘要。
- N29代码把 `CaptionMusicSuppressor.maskNativeRenderer()`放在40ms主线程循环中，在初始化阶段180ms、之后400ms重复查找；`CaptionPlayerTransitionGuard`对非紧凑转场也启动只读帧探测。

这说明补丁给播放器生命周期增加了两类额外工作：主线程原生字幕树扫描，以及普通全屏/方向/播放器类型变化的延迟稳定探测。它们不一定每次都阻塞返回，但会增加UI线程工作、延迟AI字幕恢复，并可能和YouTube自身转场竞争，符合用户观察到的详情页/悬浮窗/全屏切换更卡。

N30的低风险处理顺序：

1. 只有真正的紧凑播放器展开/收起需要延迟探测；普通全屏、横竖屏和详情页返回不再启动完整帧探测，使用一次性布局/播放器回调完成状态更新。
2. 转场期间只保留已发现字幕窗的alpha保护；暂停新的树扫描和树摘要生成。原生 `SubtitleWindowView.draw` 已有可靠防线，树扫描作为低频备用恢复，不应成为每次转场的主路径。
3. 找不到窗口时降低诊断频率，不在主线程反复导出整棵树；保留一次带原因的英文诊断，必要的详细树只在显式调试开关和采样条件下输出。
4. 任何 `stop/video/player/onPlayerType` 公共入口都不得同步等待网络、磁盘、disconnect或树扫描；现有R1 main non-blocking和CAS/退休语义继续保留。
5. 加入主线程返回时间、转场阶段、扫描耗时和下一帧延迟诊断，使用受控主线程测试验证，而不是凭“没有崩溃”判定完成。

不能删除原生字幕防护；目标是把扫描从转场关键路径移走，并减少不必要的等待和观察，不恢复N27的播放器避让功能。

## 6. 新增视频样本：1:57缺字幕的确定性根因

用户补充视频 `The Truth About the Bezelless Concept Phone [ngPkbaZliaU]` 的手动/自动英文字幕与诊断。手动字幕在1:52–2:07连续覆盖“ All right … This is a big … smartphone … zero bezels …”；诊断中对应翻译块为 `b7_354_387`，其 `source_breaks_before=[381]`。

token 380→381之间存在约722ms的源时间断点。翻译服务三次返回的计划都包含跨断点事件：第一次事件范围`380–387`，随后两次修复仍将`380–387`合并。生产验证按硬规则三次拒绝`crosses_source_break`，对应请求14/15/16，最终块7失败；`REBUILD_FALLBACK_BEGIN`发生在112140ms，直到127282ms才结束。用户所说的1:57附近缺字幕属于该整块fallback覆盖范围，不是单个句子的模型空响应。

因此N30增加“请求前按硬源断点拆Block”要求：Planner不得生成跨`source_breaks_before`或speaker marker的Block；真实b7样本必须在381前拆分后分别请求/缓存，断点空白保持，不能放宽Protocol硬拒绝、跨断点借时、删文本或反复请求同一非法块。修前三次拒绝和112140–127282ms fallback保留为回归证据；修后1:52–2:07合法源片段逐块进入翻译或安全空白，1:57不再因整块失败而缺失。中文旧golden和既有硬断点测试不改。
