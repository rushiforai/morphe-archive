## Inputs and attribution

Original package: `com.bol.shop`, version **2026.23.1**, build **430517**, minimum SDK **32**. Pulled from the owner's USB phone; base and both splits were verified against phone-side SHA-256 digests. Analysis and acceptance do not authorize installing anything on the phone.

Base SHA-256: `09708e32b4f2e3d58c1139ea979349354d6d6b53b5aabfbaa86bbfc63158a856`.

The baseline is [Wouter075/bol-patches, revision 350a044f83d0e3bf73816ed8be04aa10136f9b0d](https://github.com/wouter075/bol-patches/tree/350a044f83d0e3bf73816ed8be04aa10136f9b0d), originally supporting 2026.22.1. **Credit to Wouter075** for its three original patches. This integration adds coverage and correctness changes beyond that port. See [patch notes](../release-notes/bol-2026.23.1.md).

Analysis: jadx 1.5.6 full sources/resources, plus REA jadx-headless-mcp 0.7.1 inventory. REA inventory found 29,184 classes and 2,061 resources. jadx emitted 29,176 Java files with 427 decompilation errors. Raw Java is therefore an analysis aid; real DEX matching, patched assembly and runtime acceptance remain necessary. The fingerprint wrapper's obfuscation estimate was misleading: R8 app classes are extensively renamed into the root namespace. Names below are the inspected build's DEX names, not a cross-version contract.

## Consent gap

The original bundle contains **no consent-screen patch**. `jh6` retrieves consent, `ConsentResponse.toConsentData()` maps both data-usage and data-sharing settings, and `pr4.b` is the domain `isConsentRequired` flag. Onboarding and renewal use that domain state. The new control suppresses both prompts there and maps `ConsentChoiceResponse.toConsentChoice()` to the domain DECLINED value. It depends on Disable tracking. Existing server/account consent is not changed or represented as declined on the server. This is distinct from silently pressing Accept all.

Fresh-data acceptance also exposed the separate notification opt-in screen, whose offer-marketing copy survives privacy-domain flags. `vwe` builds the onboarding list from `twe`; the new control removes NotificationsPermission and Notifications before first-step selection. It preserves country/language and optional account sign-in, does not grant Android permissions, and leaves manual notification settings available. Existing grants are untouched.

Basket item/compliance consent (`com.bol.shop.basket.consent.ui.ConsentActivity`) is unrelated to advertising privacy and remains intact.

## Tracking beyond the old SDK blocks

| Path | Static evidence | Old behavior | Additional change |
| --- | --- | --- | --- |
| RudderStack initialization/config | `App.onCreate`, `f6c`, `ap4`, `kyi.c()` | No-op enqueue and remove anonymous-ID header; SDK still initializes and downloads source config | Take the existing DISABLE_RUDDERSTACK startup branch; retain enqueue/header guards |
| Persisted RudderStack queue | `kyi.c()` starts storage readers/writers and flush jobs | Enqueue-only blocking does not itself prevent earlier events being replayed | SDK initialization is skipped, so those replay jobs do not start |
| First-party Google Analytics session | `dgl` StartGA4Session, `j8i.s`, `b12.k` | Firebase SDK manifest flags do not block this shopping-API mutation | Return Unit before the mutation is constructed/sent |
| Experiment exposure beacons | `rba.b`, `nzj` SendExperimentMeasurementReferences, bucket/beacon IDs | Separate first-party experiment measurement outside RudderStack enqueue | Return Unit before the mutation is constructed/sent |
| AppsFlyer attribution identifiers | AppsFlyerLib init/getAppsFlyerUID/getAttributionId and PII/purchase/deep-link entry points | Empty dev-key initialization and selected log no-ops | Fluent no-op init, empty identifiers and expanded collection/upload entry-point guards |
| Sentry startup | App setup calls setDsn; automatic provider startup is a separate path | Empty DSN setter only | Manifest auto-init false and empty manifest DSN, plus the setter guard |
| Airship saved privacy settings | `x2g.c()` reads saved enabledFeatures; v2g flags analytics=16, tags=32, AI=512 | analyticsEnabled in constructor does not cover every feature or saved setting | Mask these bits on effective feature reads; preserve push/message-center bits and remote restrictions |
| Firebase Analytics/Crashlytics/Performance/Sessions | Manifest and Crashlytics setter | Existing blocks | Retained; no claim that this removes all Google services |
| Advertising identifiers | AD_ID and ACCESS_ADSERVICES permissions | Existing removal | Retained |

The scan of named GraphQL operations found two explicitly measurement/analytics/session operations: StartGA4Session and SendExperimentMeasurementReferences. This does not prove the absence of dynamically produced URLs, remote HTML tracking, server-side logging or future server-driven behavior.

## Retained functions and limits

- Bol API/account/order calls still reach bol; removing client analytics cannot prevent service-side operational/account records.
- Akamai/cyberfend bot protection and Firebase App Check remain for API interoperability. Their presence is not described as tracking-free; account/order behavior must be tested separately when authorized.
- Push and the Airship message center remain. Registration, push tokens and service delivery traffic can still occur; disabling analytics is not disabling push registration or every Airship contact operation.
- Firebase Remote Config remains for application configuration. WebView pages and remote HTML can carry additional tracking outside the inspected native paths; no claim of complete web tracking removal is made.
- User-selected campaign pages and price/offer promotion labels remain as described above. The removal controls target unsolicited placements and explicit paid-content lists, not all commerce content with a promotional word anywhere in its schema.
- Static presence, a successful build and a short emulator session are different evidence scopes. Logged-in recommendations, checkout, assistant streaming and every region/remote campaign variant require broader runtime evidence before claiming exhaustive runtime removal.

## Verification and acceptance

The complete local verification command set passed. Unchanged release/history, Python and Medium results were retained while affected Android and bilingual documentation gates were rerun after connected fixes. No new observer, runner, fixture or validation framework was added. All five selected patches applied to the real three-part input with **no failed patches**; patching, APK rebuild and signing passed. The installed final APK matched SHA-256 `02509be16ea4d2d81e2fcabd51ae53d0ae758086789e024110eacfc5eac26d55` and retained package/version/build/minimum SDK declarations. Its APK signing certificate was verified.

Anonymous API36 acceptance established:

- The patched app boots and remains open beyond PairIP's 30-second eventual-shutdown interval, without a Play-download/license screen or unexpected app crash.
- A fresh-data run proceeds from country/language directly to optional account sign-in, then Home through the normal guest action. Neither the privacy consent nor notification opt-in screens appears. No Android permission was granted to force this outcome.
- Home no longer shows the server-named Trending Deals merchandising slots, seasonal gift/Christmas decoration or independent View all offers footer. Category navigation and search remain available.
- The earlier unaffected path inspection loaded a koptelefoon search, the Sony MDR-ZX110 product including lower content sections, and Computer & Electronics category navigation. Prices, stock, description/specifications and organic recommendations remained. No sponsored placement was visible in those inspected views. This is bounded session evidence, not every remote campaign or region.

The unchanged observer covered the main app and its app-owned Akamai process before UI input. Final Home process IDs were 3737 and 4085; fresh-onboarding process IDs were 4157 and 4388. The standard Frida CLI was 17.9.11, the server 17.23.3, and the compiled observer used the pinned existing Java bridge. Observation overhead is not a startup performance measurement. Crash buffers were empty; exit evidence distinguished planned install/force-stop exits and normal isolated WebView reclamation from app crashes. Sessions ended before their recorded deadlines, with clients/scripts, tracing server, forward, logcat and task emulator stopped. The task used an owned clone and left the original reusable baseline and the separate concurrently running emulator alone.

Initial acceptance found and drove the notification, Home merchandising/background and footer fixes above. Setup-only failures (clone snapshot configuration mismatch, synchronous client callback stall and a deliberately paused launch reaching Android's startup timeout) were stopped and retained separately; none was counted as passing evidence. Raw bounded diagnostics and artifact/source bindings are kept privately in the local acceptance receipt and are not release assets.

Educational Spot & Shop, wishlist and assistant tips remain, as do optional sign-in, category navigation, user-selected Deals/campaign pages and real offer/checkout pricing. Logged-in recommendations, assistant streaming, checkout, every remote variant and exhaustive packet-level tracking absence are not runtime-qualified. The tracking changes are supported by the inspected and assembled entry points described above; they are not a claim that all service-side or WebView data processing is eliminated.
