# Gboard 18.8: the access-point VerifyError that hid the toolbar

Date: 2026-11-22 · Build: 18.8.0.1022711984-beta (176124766) · Device: CPH2747, Android 17

## Symptom

After installing a build with the toolbar patches applied, the phone reported that the keyboard
was "malfunctioning": the access-point row (toolbar) above the keys was gone, and with it the voice
key, so neither the custom top-row keys nor Rambler voice typing appeared to exist. The keyboard
itself still typed.

## Evidence

`adb logcat` on the phone, on every `onStartInputView`:

```
E ModuleManager: java.util.concurrent.ExecutionException:
  java.lang.VerifyError: Verifier rejected class aagb:
  aagb aagb.m(android.content.Context, aaiz, ackz, auco, auco) failed to verify:
  [0x3A] register v3 has type Reference: wim but expected Reference: auco
  (declaration of 'aagb' appears in ... base.apk!4)
    at aeoo.v(PG:26) -> aeoo.m(PG:292) -> ihw.x(PG:68) -> afae.onStartInputView(PG:432)
```

No `FATAL EXCEPTION`, no crash — the class simply refuses to load, so the module that builds the
access-point order never runs. Everything the toolbar provides (including the mic) disappears.

## Cause

`aagb` is `com/google/android/libraries/inputmethod/accesspoint/impl/AbstractAccessPointOrder`, the
factory that assembles the access-point list. The 18.5.4 port injects a runtime delegate at the top
of `aagb.m(...)` and cast the delegate's result back with a literal type:

```kotlin
check-cast p3, Lwim;
```

On 18.6.3 that parameter was `Lwim;`. On 18.8 it is `Lauco;`. The two builds still contain a class
named `wim`, so nothing failed at patch time — morphe happily emitted a cast to the wrong type,
`ValidateDex` passed, and the APK installed. Android 17's ART verifies the method exactly and
rejects the entire class.

Verified in the two builds with dexlib2:

| Build | `Laagb;->m(...Lauco;Lauco;)Laagb;` |
| --- | --- |
| pre-fix (`final16`) | `CHECK_CAST Lwim;` |
| fixed (`final17`) | `CHECK_CAST Lauco;` |

## Fix

The cast type is now taken from the target method's own signature instead of a literal:

```kotlin
val orderType = parameterTypes[3]
require(orderType.startsWith("L") && orderType.endsWith(";"))
...
check-cast p3, $orderType
```

## Why the emulator did not catch it

The same pre-fix APK on the arm64 emulator shows the toolbar normally and logs no `VerifyError`:
that image's ART accepts the mismatched `check-cast` and only fails if the cast actually executes
with an object of the wrong type. The phone's Android 17 verifier rejects at class load instead.
So a green emulator run is not evidence for this class of bug — the phone (or `dexdump`/dexlib2 on
the emitted instructions) is.

## Rule for future ports

Never hardcode an obfuscated type in injected smali. Derive it from the resolved target
(`parameterTypes`, `returnType`, a binding's `descriptor`). A stale name that still exists in the
new build is invisible to existence checks and to `ValidateDex`; it only shows up as an ART
`VerifyError` on the target device, and it takes down every feature that depends on that class.

## Second stale literal, currently dead code

`GboardRamblerResetHeader.preservePendingRamblerResetCleanup` still contains
`instance-of/check-cast ... Les;` written when `es` was a Runnable capture object. In 18.8 `es` is
`extends daz implements dba`, i.e. an `IResultReceiver` Binder stub with no `b`/`c` fields, so the
guard can never match and the fallback branch is skipped. Nothing crashes: the `instance-of` fails
first, and no patch calls this function — only `clearRamblerResetHeaderWithoutShowing` is used
(by `GboardRamblerOfficialSelectorPatch`). It is left as a concrete example of the same class of
bug: a literal type that once existed, silently turned into a no-op instead of a VerifyError.
