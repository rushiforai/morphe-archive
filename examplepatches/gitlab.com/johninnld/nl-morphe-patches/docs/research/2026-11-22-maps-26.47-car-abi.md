# Native car UI on 26.47: ABI port status

Working notes for porting `Native navigation for any Android Auto host` (`car/NativeNavigationPatch.kt`,
`car/NativeContentBindings.kt`) from 26.44.06.1006895251 to 26.47.00.1022347503. Static analysis of the
supplied APK; the patch stays gated to 26.44 until every check below resolves.

## Method

`map-2644-2647.tsv` (content-based class map) was used to translate the patch's type literals, then
every `requireField`/`requireMethod` was rebuilt as a reference and checked against the target DEX with
a small offline checker (`RefCheck`). 64 require-references were generated: 52 resolve as written, 12
do not.

## What does not resolve yet
1. **Display surface** `besz` — **redesigned, not renamed**. A shape probe over the whole APK
   (classes with `a..d:Object` plus two `[I` getters plus a `Surface` accessor) returns **no match**;
   the only class with the `a..d:Object` + `Surface` setter shape is `zv`, a `$cid` lambda. The closest
   remaining candidates are `beuz` (a:I, b:I, c:Object, d:Z, e:beuw, f:Z, g:bwlm), `cvwj` (a:Object) and
   `bwll/bwlm` (AR/imp surface plumbing). The original note follows. 26.44 `besz` has `d()Surface`, `b()[I`,
   `c()[I`, `f(Surface)V`, fields `a..d:Object`, and a 7-argument constructor
   `(DisplayManager, String, I, I, I, Surface, X)`. In 26.47 no class has `d()Surface`, no 7-argument
   constructor containing a `Surface`, and the closest setter candidates (`beuz.c(Surface)`,
   `cvwj.I(Surface)`, `bwlm.a(Surface)`) have unrelated field sets. The surface model was replaced by
   a different abstraction, so the two rewrites that touch it (the `besr` surface handover and
   `bete`'s `j:` holder) need a fresh design rather than a symbol swap.
2. **`uvs`** (return type of the local-search call in `rjs`) — not in the map; find the no-arg
   `aM()`-style getter's new return type.
3. **Native content models** `qdf/qbn/qcq/qbh/qcr/qbj/qaq/qbo/poe/qca/qbc/snk` — `qdf`→`qfp` and
   `qbn`→`qdu`/`qbj`→`qdr` are mapped but unverified; `qcq/qbh/qcr/qaq/qca` are not in the map at
   all (the native recents/search row models were restructured).

## Picker (Better offline maps) — structural note

The 26.47 layout lambda is `Lcoa;->a(Object)Object` and its instruction flow is:

```
48  iget-wide  v11, v8, Laptd;->d:J          ← size cap
62  cmpg-double v2, v3, v11
63  if-lez     v2                            ← area-vs-cap test
70/74 invoke-static Math.sqrt                ← the shrink
96/97 move v21←v2 ; v2←v21                  ← "not too big" path (flag rewritten on the 2nd move)
98  iget-object v0, v0, Lcoa;->c:Object      ← local selection state
99  invoke-interface Ldtg;->b(Object)V       ← local state write
101 invoke-static Lavcx;->cQ(Ldtg;)Landroid/graphics/RectF;
112 invoke-virtual Laptd;->f(Landroid/graphics/RectF;)V   ← window selection write
113 sget-object Lcujx;->a ; return-object
```

So the 26.44 patch's three steps still have equivalents: the cap test (`62/63`), the local state write
(`99`, state setter `Ldtg;->b(Object)V`), and a window write that is now the model call `aptd.f(Rect)`
(`112`) instead of a state field. A 26.47 branch can install `pickerRect` before `99` and
`pickerOverlay` after `112` (reloading the state from `Lcoa.c` and the activity from `Laptd.a`), and
only needs the "not too big" check relaxed, since the flag register is overwritten on the second move.

## Shape-search correction (26.47)

An earlier note in this file claimed the row-model shapes had no match. That was **wrong** — the probe
required one method to match every pattern at once instead of the class containing a method for each.
With the corrected probe (`ClassHas`, each pattern matched by any method) both shapes do exist:

- `b()L<row>;` + `c()ImmutableList;`: many candidates (`aiix`, `ajju`, `ajiu`, `ajja`, `algg`, `awcg`, …);
- `g()String; h()String; i()String; j()V`: many candidates (`qfb`, `qfu`, `qqm`, `qqv`, `tcl`, `akwy`, …);
- ClassMatch for `qbh`/`qcq`/`qcr` scores only 0.06–0.08, so content matching cannot pick between them;
  the disambiguator must be their *use* (which class the car window stores / which row type it binds),
  not their method names alone.

`bhhr→cgl` is confirmed on the hook side: `Lpyg;->a(Lcgl;)Ljava/lang/Object;` and

## 26.46 bisect result (which release redesigned what)

Extracted `base.apk` from the supplied 26.46.00.1016872485 bundle and ran the same shape probes:

| Shape | 26.44 | 26.46 | 26.47 |
| --- | --- | --- | --- |
| `besz` (fields `a..d:Object`, ctor `(DisplayManager,String,I,I,I,Surface,X)`, `b()[I`, `c()[I`, `d()Surface`, `f(Surface)V`) | present | **present as `bfce`** (identical shape) | **gone** — no `d()Surface`, no two `[I` getters |
| `qbh` (`b()L<row>;` + `c()ImmutableList;`) | present | **no match** | no match |
| `qcr` (`g()/h()/i() String` + `j()V`) | present | **no match** | no match |

Conclusions:

1. The **row/recents models (`qbh`, `qcq`, `qcr`) were already redesigned by 26.46** — three releases
   removed from 26.44, so they cannot be recovered by diffing 26.44↔26.47 alone.
2. The **car display surface model** held its exact 26.44 shape through 26.46 (`bfce`) and was
   redesigned **between 26.46 and 26.47** — that is the narrowest window and the best place to look
   for the new abstraction (compare `bfce` in 26.46 with the 26.47 classes that replaced it).

The same bisect also means the mapping table should be built 26.46→26.47 for the car cluster, not
26.44→26.47, because 26.46 already carries the intermediate names.

## Why the row models cannot be matched positionally

`qfp` (the `qdf` candidate) shows the alignment broke, which is the real reason the remaining refs
fail:

| 26.44 `qdf` | 26.47 `qfp` |
| --- | --- |
| ctor `(Lbhfu;, Lbdbi;, Lbdbb;, Context, Lqgm;, Lqoz;, Lsiy;, Lsiy;, …)` | ctor `(Lbhsn;, Lbdov;, Lbdoq;, **Lpro;**, Context, Lqiw;, Lqrh;, Lxch;, Lxch;, …)` |
| `d()ImmutableList` | `e()ImmutableList` |
| `e()String` | `f()String` |
| `f()I` | `h()I` |
| `g()V` / `h()V` | `g()Z` / … |

An extra parameter (`Lpro;`) was inserted before the `Context`, and the whole getter sequence moved by
one. So the row models the patch validates must be identified **through `qfp`'s fields and its model
getters' new positions**, not by their own method names — which is exactly why every shape search
returns a crowd and ClassMatch scores 0.06–0.08.

Practical next step for the next session: from `qfp`'s ctor/methods take the values it stores
(`e()ImmutableList` → the recents list model) and follow each to its class, then bind those to
`qcq/qbh/qcr` by role (list, row, row-binder), and verify with RefCheck. This is a role assignment,
not a name lookup.

## New lead: the row type is probably `bhui`

26.44's three row binders (`qca`, `qbc`, `snk`) are anonymous lambdas: they implement `Lbhia;` and
expose `a(Lbhhr;)Object`. In 26.47 there is a large family of `a(Lbhui;)Object` lambdas
(`agkm`, `aglc`, `aglu`, `agnl`, `agoj`, …), which makes `bhhr → bhui` the likely row type
(`cgl`, used earlier, is unrelated — `pyg`/`okg` have no such method).

So the next pass should: take the interface these 26.47 lambdas implement, find the three instances
that are constructed in the car window/pager code, and hook those — the same roles `qca/qbc/snk`
play in 26.44. That also settles `NativeContentBindings`' `bhhr` reference.

## Row-binder internals (new)

`qca.a(bhhr)Object` casts the row to **`qcq`** and reads `qcq.e()String` / `qcq.f()I` in its switch —
so `bhhr` is the row *base* interface and `qcq` is the concrete row interface with
`d()ImmutableList`, `e()String`, `f()I`.

That gives a much sharper shape for the 26.47 row interface (and hence for the binders that take it),
but the exact triple no longer matches: 26.44 answers `qcq` and `qdf` for
`d()ImmutableList + e()String + f()I`, while 26.47 answers **nothing** — one of the three members
changed type or name again. Next step is to relax that triple (drop `f()I`, or accept `List`,
`CharSequence`) and then pick the class the car pager casts to in its row switch, exactly as `qca`
casts to `qcq`.

## Relaxed-triple result

Dropping `f()I` and keeping `d()ImmutableList + e()String` gives four 26.47 classes, and the car-package
one (`aqya`) has exactly the row shape with one drift:

```
Laqya; extends Object [Laqye;]      (aqye = empty marker interface)
  d()ImmutableList   ✔ matches 26.44 qcq.d()
  e()String          ✔ matches 26.44 qcq.e()
  f()V               ✘ 26.44 qcq.f() returns I
  b()Layuh;  c()Lbabo;  a(Laqxr)Laqxr;
```

So the row interface drifted only in `f()`'s return type (`I → V`) and its marker is `aqye`. That is
the sharpest candidate yet for `qcq`, and the binders should cast to the same interface. The very next
check is to confirm `aqya` is what the 26.47 pager casts to in its row switch (26.44 `qca` casts to
`qcq`), and whether `bhhr` is `aqye` or a sibling marker.

## aqya ruled out as the binder row

Only eight classes reference `Laqya;` and none of them is an `a(Lbhui;)Object` binder:

```
Lmea  a(Object)ListenableFuture      Lalwb  apply(Object)Object
Lavdq cs(Laqya)V, cw(Object)I        Lapiv  a(Object)ListenableFuture

## qfp implements qfa — the window *is* the recents model

```
Impls(Lqfa;) → Lqfp;   (the only implementation)
```

So, exactly like 26.44 (`qdf implements qcq`), the captured "recents model" in 26.47 is the window

```

```

`qfb` is the neighbour of `qfa` and the most likely recents row item; its letters need one check
against 26.44's element before the extension switches over.

## Recents row item settled: `qcr → qfb`

```
26.44 Lqcr;  g()String  h()String  i()String  j()V     ← exactly the letters NativeCarContent reads
26.47 Lqfb;  ... g()String  h()String  i()String  j()V  (+ a-f: focus listener, builders, ...)

## Navatar: the real lever is the guard, not the latch (26.47)

`is_navatar_enabled_state_reset_for_android_auto` is `Lbace;->ix:Lbabv;`, found from the `<clinit>`
string table (`const-string` then `sput-object Lbace;->ix`). It is a one-shot migration latch:
`Lvot.e(DRIVE)` records it and bumps a metric. Forcing it does not change what the car shows.

What decides the empty model is the controller's private guard:

```
Lvot.u(ckmg) = carFlag && d.u() == pnj.c && c(ckmg) == vpg.b     // vpg.b == AUTO_ENABLED
```

called from `a()` (colour id, `bace.iu`) and `e()` (model name, `bace.it`). Both are gated, and only
those two call it.

26.44 counterpart: controller `Lvok;`, mode `Lckbl;`, enum `Lvox;` (map 0.92), same shape and the same
two call sites — verified present in the 26.44 APK (`Lvok;->u(Lckbl;)Z`, `Lvok;->e(Lckbl;)Ljava/lang/String;`).

The option prepends `const/4 v0, 0x0` / `return v0` to that guard, so both callers take the
"chosen by the user" path and return the saved model and colour.

### Custom navatars

Not reachable from this flag. Models are server assets with a manifest and textures
(`CustomizableChevronPromo.model_manifest`, `NavatarsLoadModelMissingTextureCount`), no navatar assets
ship in the APK, and names map through a fixed switch (`vps.p`, unknown -> 1). Preselecting a built-in
model is cheap; adding our own is an asset-pipeline project.

## Phone and car round on 26.47: six runtime ABI defects

Patching succeeded while the app died at four successive points. Every one was an ABI assumption the
verifier or the reflection layer only exposes at run time; the patch and its unit tests never see them.

1. `VerifyError` in `SavedOnMap.item` — `Enum.valueOf` is typed `java.lang.Enum` and 26.47 declares the
   personal-place builder field as the enum itself, so the generated code needed a `check-cast`.
2. `VerifyError` in `avbe.e(F)` — the hide-ads guard returned before the promoted-pin hand-off using
   `v0`, which is that virtual call's receiver. The guard now picks a free local.
3. `VerifyError` in `asju.e()` — the place-sheet Ask action's only register is `this`; the entry guard
   overwrote it. Both Ask gates now rewrite the answer on its way out (`false` stays false,
   `true` becomes `!HIDE_AI`).
4. `IllegalStateException: Maps native dispatch ABI` / `NoSuchMethodException: bngr.d` — the extension
   resolved the listener method by the 26.44 parameter class `bnas`. It now resolves by shape
   (one-argument method the argument satisfies), and the remaining 26.44 names in the coordinator
   (`bnav`, `blvb`, `ycj`, `bjpp`, `bjpk`, `bmon`, `bmzb` player classes) take a name list that covers
   both releases.

Validation used two offline checks over the patched DEX:

- a guard scanner that reports a `Shapes.HIDE_*` guard register later consumed as a reference, both
  linearly and in the block its branch jumps to: 2 findings before the fixes, 1 after the first, 0 now
  (19 guards, 346,728 methods);
- a shape probe over the 26.47 listener interface: all four concrete player classes have a one-argument
  `d`, and the job class has `e(Lbnil;)V`, so the new reflection lookups resolve.
5. Car host: `onAppCreate failed` with `NoSuchMethodException: GoogleMapsApplication.rS`. The gearslip
   guidance bridge used 26.44's cached component accessor. 26.47 inherits `pY()` from `nup` (which
   returns `nup.n()`'s `crin`), so the accessor is now tried as `rS` then `pY` in both the car bridge
   and `MapsGuidanceCoordinator`. The same bridge also needed the renamed listener ABI
   (`blra`→`blxx`, `blrb`→`blxy`, callback `se`→`qk`) and a shape check instead of the `awxs` name for
   the distance utility. Verified on the APK: `Lnup.pY()Ljava/lang/Object;`, `Lngt.bR`/`Lngt.hN` both
   `Lcrkc`, and `Lblxx` implements `Lblxy` with `qk(Lblxv;)V`.
