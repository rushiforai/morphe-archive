## Scope and binary identity

ARM64 libwaze.so SHA-256: `72a28430c1fe2f0b5939141bd92c3b7000af8e64fb366f96bf4a47cd6d478e1e`. No physical phone used. No camera coordinates, reporter identities or raw memory were logged.

## Observed native path

1. `TilesInsightsProvider` typeinfo at `0x437b1f0`, vtable at `0x437b1d8`. Its enumeration method at `0x3be69c8` is identified through provider RTTI and two callback RTTI records explicitly naming `TilesInsightsProvider::Iterate`.
2. Constructor `0x3be67fc` subscribes to tile events using callback vtable `0x437b388`, invocation `0x3be7bc0`.
3. Tile additions reach `0x3be7c9c`; it walks native tile-feature records in `0xe0`-byte increments and invokes converter `0x3bed5ac`.
4. Converter receives the native feature in `x0`; ARM64's indirect result pointer is in `x8`. Feature tag at `+0xd8`: tag0 selects the camera branch. Camera type vector is at feature`+0x30` (begin) and `+0x38` (end); native helper `0x2d5fe9c` checks the camera variant and returns this vector.
5. Raw feature position is the pair at `+0x10`/`+0x14`. The header is copied into the resulting shared object; the renderer copies that pair into `TileAlertData+0x14`. The renderer callback is `0x2ed76cc` -> `0x2ed76fc`, with `WazeInsight const&` in `x1`.
6. Provider per-entry callback `0x3be831c` -> `0x3be834c` receives a `MapEntry&` whose first fields are the insight. It invokes the original consumer with that insight and copied attributes.

## Native identity and removal path

Static evidence: provider constructor stores addition callback at provider`+0x10` and removal callback at`+0x40`. Successful cache insertion calls addition through `0x2c8bc88` at callsite`0x3be7e0c` (return address`0x3be7e10`). Tile-event handling at`0x3be7c04` dispatches event1to removal, event3to removal then addition, event0to addition. These event meanings are inferred from dispatch behavior, not public enum names.

Removal function`0x3be7fb4` takes the tile id in`w1`, constructs a tile area, filters entries by shared feature header's first32-bit field (comparison at`0x3be81dc`), collects removed`0xa8`-byte MapEntry records, then invokes the removal callback for each at`0x3be80e0` (return address`0x3be80e4`). This establishes the first32-bit feature field as a tile correlation field. The64-bit field at`+8` participates in the renderer hash key; uniqueness/signedness need runtime verification.

An observational probe can filter calls to`0x2c8bc88` by those two exact return addresses to distinguish additions/removals and copy only the insight's point/type/identity fields. This would avoid the area-limited enumeration path. It has not yet been exercised.

Production hook caution: `0x2c8bc88` starts with`ldr x0,[x0,#0x20]`, `cbz x0,...`, `ldr x8,[x0]`, `ldr x2,[x8,#0x30]`. Its PC-relative conditional branch cannot be copied unchanged into a trampoline. Use a verified relocation implementation or a non-code hook with equally complete lifetime/ABI handling. Never install an unvalidated fixed-size prologue copy.

Packaging: the existing raw-resource patch API can add an ARM64 native library under the APK's`lib/arm64-v8a` directory (the Flitsmeister native resource patch demonstrates library access). Waze's current extension is Java/Dex-only and has no external-native build configuration. Adding an extraction library is product work, separate from Frida observation. The native bridge must check exact binary identity and architecture, preserve original callbacks/results, and expose only bounded copied values to Java.
