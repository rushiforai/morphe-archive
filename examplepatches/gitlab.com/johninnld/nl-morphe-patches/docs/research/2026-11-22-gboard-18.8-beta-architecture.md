# Gboard 18.8.0.1022711984-beta: build map and how to navigate it

Date: 2026-11-22. Companion to the port report and the hidden-feature inventory.

## 1. Where the code is

Decompiled tree: `~/Scripts/gboard/gboard-18.8-beta/` (jadx 1.5.6, `--show-bad-code`, 4 dex).

| Path | Contents |
| --- | --- |
| `sources/` | 34 452 `.java` files; 48 718 classes |
| `sources/defpackage/` | 32 531 obfuscated classes (`La;`…`Lzzzz;` in dex terms) |
| `sources/com/google/android/…` | 11 921 non-obfuscated classes: every Gboard extension and library keeps its real package |
| `resources/AndroidManifest.xml` | decoded manifest |
| `resources/res/` | decoded resources (`xml/`, `values/`, `raw/`, `drawable*/`) |
| `resources/assets/` | theme binaries, emoji packs, `decision_rules.bin` |

The single most useful property of this build: **R8 keeps original class names in logger
tags**. 1 409 classes embed their own FQN as a string via `aukq.i("com/google/…")`, e.g.
`defpackage/ljp.java` contains `…/clipboard/ClipboardDataHandler`. Grep for the feature
name and you get the obfuscated class instantly:

```
grep -rl 'ClipboardDataHandler' sources | head     # -> defpackage/ljp.java
grep -rn 'aukq.i("com/' sources | grep -i rambler
```

`adb shell dumpsys activity service com.google.android.inputmethod.latin/com.android.inputmethod.latin.LatinIME`
prints the same tags at runtime.

## 3. The module system

Gboard is a module host, not a monolith:

- `com.google.android.libraries.inputmethod.module.ModuleManager` (obfuscated `ModuleManager`
  keeps its name) instantiates "extensions" declared in XML/proto; every feature in
  `apps/inputmethod/libs/*` is one `ModuleDef`.
- Modules implement small interfaces (`AbstractIme`, `InputView`, `Processor`,
  `Facilitator`, `LifecycleTask`…) and are looked up as
  `ModuleManager.getInstance(ctx).b(SomeModule.class)`.
- The IME delegates keyboard behaviour to `AbstractIme` subclasses in each feature module;
  settings screens are preference fragments registered the same way.

Consequence for patching: most features are reached through a `ModuleManager` lookup, so a
patch can either (a) hook a stable lifecycle point on `afae`, or (b) hook the module's own
method after resolving it by class. The existing patch set uses both.

## 6. Two representative call flows

**Keyboard start-up → feature window hook** (what most lifecycle patches rely on):
`LatinIME` → `ihw` → `afae.onCreate` → `onCreateInputView` → `onStartInputView`
(`findMutableMethodOrThrow` accepts the exact descriptor; the patch prepends its delegate and
`move-result`s into the original register).

**Flag read** (every unlock):
`SomeFeature.method()` → `Ladfs;->g()Ljava/lang/Object;` → `Ladgf;` snapshot (`a` value,
`b` priority). Our flag-family patch replaces the single `return-object` with a call into the
extension carrier, so the extension decides the value by flag *name* — no per-flag bytecode.

## 7. Navigating the decompiled tree

1. Start from a log tag or a user-visible string (`grep -rl "string you see" sources`).
2. Map the obfuscated class with `grep -rn 'aukq.i("com/'`.
3. Read the class; the `R.string._0_resource_name_obfuscated_res_0x7f…` ids point at
   `resources/res/values/strings.xml` and the XML layouts in `resources/res/xml/`.
4. For a patched feature, the port artefacts (`.tools/artifacts/gboard-port-18.8.0-beta/`)
   already contain the 18.6.3→18.8.0 class map and the resolved member table, so you rarely
   have to start from strings.

## 8. Scale note

"All functions" for this APK means 48 718 classes / several hundred thousand methods. This
document maps the subsystems, the entry points, the module system and the flag surface, and
the port artefacts map every symbol the patch set touches. Function-level comment sweeps of
the remaining ~46 k classes would be a large, mechanical effort with little value for
patching; the useful grain is per-feature (module → entry point → state machine), which is how
the research notes under `docs/research/` are organised.
