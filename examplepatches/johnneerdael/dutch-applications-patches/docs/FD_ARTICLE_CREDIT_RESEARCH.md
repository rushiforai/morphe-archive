# FD article credit research

**Archived, 2026-10-28:** The user removed FD from the active project scope. This report preserves prior evidence and uncertainties; it is not a pending investigation or implementation plan. Resume only at the user's explicit request.

2026-10-28. Target: `nl.fdmg.fd` 2.59.0 / 161, minSdk 29. Read-only shipped-code inspection with leanrea and a bounded live inspection of the USB Android device, using the user's existing login. No app installation, patch, logout, data clearing, purchase, token alteration or manual mark-read request was performed.

## Conclusion

**Seen:** the live app received a response that its native response parser classified as `OUT_OF_ARTICLES`. This was observed in logcat after opening an article, independently of the visible credit-exhausted screen. **Inferred:** changing a local credit display, paid-user boolean or local navigation gate does not change that server decision under the traced shipped protocol. No client-generated numeric balance is present in the article request contract or traced header builder.

This is evidence of a server-returned access refusal, not an absolute proof that every alternative delivery path is unavailable. In particular, the complete authenticated response was not captured, so absence of `contents` in that response remains **unknown**. No successful full-body bypass was demonstrated.

## Seen: live behavior and response provenance

- The installed base APK SHA256 is `6541537290309d49c5f6fa82ac84b720319df026da515c9a9b672890954d4cfa`, identical to the saved original base APK used for the static inspection.
- Initially, and again after opening the home lead article, the native UI displayed resource `upsell_title`: “Uw artikeltegoed is op of uw abonnement is verlopen”.
- The latter open produced three `AccessDecisionHelper` log entries at device-log time `10-28 03:08:32`, each reporting `APIError(... reason=OUT_OF_ARTICLES, access=ArticleAccess(decision=null, reason=null), ...)`. The three entries are compatible with article-pager prefetch; their individual request URLs were not logged.
- This value is read from a real response: `Ljl/b;->a(Lokhttp3/Response;)Z` calls `Response.peekBody(Long.MAX_VALUE).string()`, then `Lcm/a$a;->a(String)APIError`, and logs the parsed result. It is not generated by the upsell UI or inferred from the user's description.
- The authenticated HTTP status is **inferred as 401** from the shipped flow: `Ljl/c;` is the configured OkHttp `Authenticator`; the UI mapper `Lcm/a$a;->c(...)Fragment` recognizes access errors only when `HttpException.code()==401`. An independent authenticated status line was not captured.

The production APK is not debuggable (`run-as` is denied); no root or Frida process was available. FD exposed no WebView debugging socket. `NetworkModule.n()` sets native HTTP logging to `Level.NONE`, and its network security configuration trusts system certificates only. Existing account credentials/cookies were not extracted. Thus no same-account replay or authenticated request-claim variation was possible in this inspection without changing the installed app or device trust configuration.

`Ljl/b;` also prevents pointless token refresh for recognized access refusals. Its `OUT_OF_ARTICLES` handling considers existing federated-access details and stored login state. `Ljl/c;->authenticate(...)` returns no retry request when this helper accepts the refusal; otherwise it can refresh the real token and retry with the real stored credentials. The federation claim reader `Ljl/h;->a(String)Ljl/g;` handles organization/expiry information, not a numeric quota.

## Seen: success, local gates and refusal branches

- `Lnl/fd/data/service/UserServiceImpl;->a()Z` means **isLoggedIn**, implemented as actual authentication-store presence. The earlier description of this predicate as a possible paid-access test should not be used: it is a login test.
- `ArticleActivity.p0(WebLink)Z` and `Ldn/l;->f(I)Fragment` can replace navigation locally when `settings.paywall_enabled` is true and the user is not logged in. The traced logged-in path already proceeds to content retrieval. Forcing this setting false changes local navigation, not the server quota decision.
- On success, `ArticleResponse.f()` returns the received `contents`; `NativeArticleFragment.r1()` routes into native `j1()/x0()` mapping or the web-required path. `ArticleResponse.k()` is **webViewRequired**, not an entitlement switch.
- On failure, `NativeArticleFragment.o1(Throwable,Z)` stops loading/read timers and calls `Lcm/a$a;->c(...)Fragment`. `APIError.reason` is deserialized from top-level JSON **`message`**. `ErrorReasonDeserializer` uses exact enum names, with unknown strings mapped to `OTHER`.
- Mapper branches are: `NOT_LOGGED_IN` / `MISSING_DIGIKRANT_ROLE` → registration; `OUT_OF_ARTICLES` / `OTHER` → trial upsell; `NOT_WEEKEND` → weekend upsell; `MISSING_ARCHIVE_ROLE` → archive upsell. Suppressing these promotional fragments can expose the existing preview/error fallback; it does not manufacture a successful `ArticleResponse`.

## Seen: bounded independent API and website checks

For sample article `1617287`, both an anonymous baseline and the exact shipped guest fallback header returned **HTTP 401**, **93-byte JSON**, keys `message,access`, `access.decision=NOT_AUTHENTICATED`, `access.reason=User is null`, and **no `contents` key**. Both decoded response hashes were `204363ba0f9e4fc3b167c5b6b434261c5e344316dc00498f11be9eaffebb3a49`. This corrects the earlier probe omission of the shipped guest header; adding it did not change the result. These are guest results, not authenticated quota results.

There is a distinct shipped website transport: `FdWebApiClient.getPage(String)` performs GET on a supplied URL; `service/x0.C0()/o()` support that first-party resource path. Two requests to the sample's actual `fd.nl` article URL returned:

- Public browser headers: HTTP 200, 187,293 bytes, root `no-access` / `upsell-login` indicators, no `articleBody` field.
- Shipped native guest headers: HTTP 200, 2,442 bytes, one empty `<article>` element, no `articleBody` field.

Neither response demonstrated a delivered full article. No logged-in website request, executing web-session comparison or exhaustive alternate-endpoint search was performed. The other traced native delegates `service/x0.j()` and `s()` both call the same `getArticle` contract.
