# Printer trace and comparisons: design notes

These notes describe the next phase. No telemetry is currently sent and no collection endpoint or comparison website has been deployed.

## What we can observe

The patch sees supported single-object SNMP GET calls in Brother Print Service Plugin. It records request start and end offsets, the OID, whether the cache or printer answered, outcome and, when available, the captured response. This is app-hook activity, including cache hits for which no network packet exists. It does not contain all device discovery traffic, other protocols, arbitrary SNMP exchanges or the precise time a preview appeared. Bursts are groups separated by a three-second idle gap, not proven print previews. History currently retains up to 20 bursts per printer.

## Dictionary

Definitions live in [`data/oid-dictionary.json`](../data/oid-dictionary.json), with numeric object prefixes, symbolic names, plain-language names, descriptions and a source URL. Add or correct an entry there and run `python tools/generate_oid_dictionary.py`; commit the generated Java and use `--check` to validate it. Object instances are matched at dot boundaries using the longest defined prefix. Optional `values` objects map integer strings to meanings, with a separate `values_source` URL; unlisted values remain raw. Brother-specific entries are based on the service’s observed use in version 1.17.0 and are not represented as official Brother MIB definitions; see [Brother OID evidence](BROTHER-OID-EVIDENCE.md). Unknown or unverified vendor-specific identifiers remain unknown. Review a source and its licence before adding a definition. Do not put printer captures, credentials, private addresses, serial numbers or responses in a pull request.

## Trace presentation research

[Wireshark](https://www.wireshark.org/docs/wsug_html/) uses a chronological packet list, filtering and an expandable detail view; its [SNMP display filter reference](https://www.wireshark.org/docs/dfref/s/snmp.html) shows available protocol fields. [Net-SNMP snmptranslate](https://www.net-snmp.org/docs/man/snmptranslate.html) resolves numerical OIDs using MIB modules. These suggest a chronological request list with time from burst start, human name and raw OID, cache/printer source, duration and outcome; selecting a row opens its detail. Search and filters, a graphical timeline, response decoding and richer comparison can follow. Labels and offsets must not imply that app-hook events are packet captures or that an activity burst is necessarily a preview. The in-app request list can also show a simulated sequential uncached timeline: it adds live request durations and prior printer-time samples for cache hits in recorded order. These cumulative offsets do not reproduce overlaps or pauses. Where a prior sample is missing, the duration and subsequent cumulative offsets are unavailable. The request detail and structured export retain the original observed offsets.

## Export formats

[pcapng](https://www.wireshark.org/docs/man-pages/tshark.html) is a standard format for actual captured network packets and can be opened in Wireshark. Packet-level analysis requires a separate network capture tool. Our cache hits have no packets and our instrumentation does not preserve full raw SNMP packets, so turning this activity into a pcapng file would invent traffic. Continue to export the current versioned JSON for full recorded burst data, and CSV for simple event analysis. As a future interoperability experiment, evaluate [OpenTelemetry spans](https://opentelemetry.io/docs/specs/otel/trace/api/) for start/end timings and parent-child activity; do not describe that as a packet capture. Validate a sample with real tools before promising compatibility.

## Opt-in comparison concept

The user selected **timings and request types only** as the contribution default and requested design first, without deploying. The switch starts off. Explain the exact fields before enabling, how often submissions happen and how to turn it off. Never collect or upload printer responses, documents, SNMP community strings, local IP/MAC addresses, serial numbers, hostnames, Wi-Fi identifiers or diagnostic logs in the default contribution. The model and firmware are useful comparison dimensions but should be explicitly shown for review and included only if the user agrees; if unavailable, report unknown rather than infer. Use an explicit schema allowlist, not a filtered copy of a full local export.

A proposed contribution consists of a schema version, patch/app version, an explicitly shared model/firmware when available, a random submission identifier, and per-burst request sequence entries: numeric OID, source (cache or live), elapsed request duration, offset within the burst and outcome. Avoid exact wall-clock times by default. OIDs can encode indexes and unusual configurations; the opt-in explanation and review should say request identifiers are included. The uploader should queue bounded submissions locally, use HTTPS, retry with backoff and stop future uploads when disabled. Define whether enabling submits old history or only future activity before implementing; do not assume historical consent.

The receiving service would validate and cap payloads, reject fields outside the schema, rate-limit, retain data for a documented period and support deletion. No permanent device identifier is needed for model-level aggregation. A private, unguessable contribution receipt could allow the contributing user to reopen their own timeline and request deletion; avoid embedding receipt secrets in server logs or publicly shareable URLs. Users should choose whether a timeline is shared; public comparison pages can expose aggregates separately.

Comparison pages should make workload differences visible: model, firmware, app/patch version, number of printers and bursts, request counts and per-live-request latency distributions (median and percentiles with sample counts). Separate live requests from cache hits and separately label estimated saved request work. Avoid comparing total time across bursts with different OIDs or counts, and do not claim request durations are preview time. Include caveats for sleep/wake state, network, concurrent requests, firmware and small samples. A timeline should place overlapping request spans on the same time axis and offer filters by OID/name, cache status and outcome.

Before building the upload client or deploying infrastructure, agree the hosting, retention period, public/private comparison behaviour, consent wording, revocation and deletion process. The owner chose to design the service first, so this document does not authorize deployment.
