# AGENTS.md

How to work on this repository — for humans and for AI agents.

If you only want to use the patches, read the [README](README.md) instead. This file covers
the toolchain, how a Morphe patch actually works, how to test on a real phone, and the
conventions the repository follows.

## What this repository is

- A **Morphe patch bundle** for five Android apps. It contains Kotlin patches that edit
  Dalvik bytecode and decoded resources, plus one Java extension that is merged into the
  patched app as extra classes.
- **Not an app, and not a fork of the apps.** The build output is `patches/build/libs/patches-<version>.mpp`
  (a JAR/DEX container). Morphe applies it to a stock APK/APKM/XAPK, repackages the result and
  signs it with Morphe's key.
- **GPLv3.** Ported patch sets keep their upstream attribution in the source file headers,
  [NOTICE](NOTICE) and the README credits. Add attribution when you port code.
- **An AI-assisted experiment.** Much of the code, analysis, documentation and test
  reporting here was produced with an LLM coding agent as an end-to-end experiment. Treat
  claims in the repository as things to verify, not as guarantees — see the README
  disclaimer.

## Repository map

```text
patches/src/main/kotlin/dev/hyzor/patches/
  <app>/shared/Constants.kt           Compatibility (package, versions, APK type) + descriptors
  <app>/<feature>/Fingerprints.kt     the matchers for that feature
  <app>/<feature>/<Name>Patch.kt      the patch itself
  util/                               small DEX helpers shared by patches
patches/src/main/resources/           files bundled into the .mpp (drawables, XML, …)
extensions/chesscom/                  the Java extension (compiled to a .mpe and merged)
tools/verify_fingerprints.py          offline class/method fingerprint check
.github/scripts/                      README patch-list generator
.github/workflows/                    release + dev→main PR automation
patches-list.json                     generated by the release CI — do not edit
patches-bundle.json                   generated by the release CI — do not edit
README.md                             user docs; the patch list block is generated
docs/apps/                            per-app technical write-ups
.tmp/<app>/                           working directory: stock and patched APKs, harnesses (gitignored)
```

`.tmp/` is the working directory for everything temporary: stock APKs and XAPKs, patched
outputs, decompiles, harnesses and logs. Keep one folder per app, named after the app
(`.tmp/chesscom/`, `.tmp/duolingo/`, `.tmp/nytimes_games/`, `.tmp/sleep_as_android/`,
`.tmp/snorelab/`), instead of dropping files at the top of `.tmp/` or in the repository root.
It is gitignored: nothing the build needs may live there, and it is never committed.

```

export GITHUB_ACTOR=your-github-username
export GITHUB_TOKEN=$(gh auth token)   # logged in with read:packages
```

## Building

```bash
./gradlew :patches:buildAndroid
```

Outputs:

- `patches/build/libs/patches-<version>.mpp` — the bundle for Morphe.
- `extensions/chesscom/build/morphe/extensions/chesscom.mpe` — the compiled extension,
  folded into the bundle at `extensions/chesscom.mpe` (the path stored in
  `Constants.EXTENSION_FILE`). The build folds it in; you never copy it by hand.

The version comes from `version` in `gradle.properties`, and is bumped by the release
pipeline, not by hand. `./gradlew :patches:generatePatchesList` regenerates
`patches-list.json` from a built bundle — the release CI does this; don't run it for normal
changes, and don't commit the result.

`./gradlew clean` removes build outputs (and with them the artefacts you were testing).

## How Morphe patching works

### The pipeline

```text
stock APK/APKM/XAPK ──► Morphe + patches-<version>.mpp ──► patched APK (re-signed)
                              │
                              ├─ bytecode patches  : match a method, rewrite its smali
                              ├─ resource patches  : edit decoded XML / manifest / files
                              └─ extensions        : merge extra DEX classes into the app
```

Morphe Patcher (built on smali/dexlib2 for bytecode and ARSCLib for resources) receives the
APK and a set of patches. Each patch's `execute {}` block mutates the patch context: mutable
class definitions, decoded resources, or raw files. The patcher then hands back the modified
dex and resource components, which Morphe repackages and signs. The patched app is therefore
a new APK with a new certificate — that is why apps must be uninstalled first, and why
integrity checks inside an app start to fail.

### Patch types and lifecycle

- `bytecodePatch { }` — edits DEX. Most patches here.
- `resourcePatch { }` — decodes resources and edits them (XML, manifest, arbitrary files).
- `rawResourcePatch { }` — edits files without decoding resources (cheaper; none are used here).

Each patch declares:

- `compatibleWith(...)` — the `Compatibility` from `shared/Constants.kt`. Patches without it
  are treated as universal, so always declare it for a user-facing patch.
- `dependsOn(...)` — dependencies run first, and a failing dependency skips the dependent
  patch.
- `extendWith("extensions/chesscom.mpe")` — merges the extension DEX before `execute` runs.
- `execute { }` — the work. `finalize { }` runs after all dependents (used by the chess.com
  clone patch to rename the package once every other patch has finished).
- `name`, `description`, `default` — what Morphe shows users. Patches with `name = null` are
  internal helpers and never appear in the patch list or the README.

Options (`stringOption`, and the other `option` builders) are shown in Morphe's UI and are
available in `execute`. Duolingo's *Type* option (Super / MAX) is the example here.

### Fingerprints

A `Fingerprint` is a declarative matcher: class, method name, return type, parameters,
strings, referenced methods/fields, and instruction filters with positions. The patch then
uses `.method` (or `.classDef`, `.matchAll()`) to get the mutable target. This is what makes
patches survive obfuscation and small app updates.

Rules that matter in this repo:

- Put fingerprints in the feature's `Fingerprints.kt`, named `…Fingerprint`, and document
  why a shape was chosen when it is not obvious.
- Prefer structural anchors (return type, parameter list, string literals, field usage)
  over obfuscated names. SnoreLab and Duolingo depend on this; name-based matching would not
  survive an update.
- A fingerprint must match **exactly one** method. Duplicate matches only fail when Morphe
  is run with `--validate` (or when you use `matchSingle()`), so a duplicate can otherwise
  patch the wrong method silently. Use `--validate` when testing.
- When a hook is optional across versions, resolve it with `methodOrNull` and degrade to a
  no-op rather than failing the whole patch (see Sleep as Android's optional signature and
  cloud hooks, which are missing from some targets).
- `tools/verify_fingerprints.py` checks the class/method anchors without Gradle or Morphe.
  It is a fast pre-check, not a replacement for building and applying the bundle.

### Extensions

An extension is precompiled code merged into the patched app, so the patch itself only has
to insert a call. The chess.com extension is a Java Android library under
`extensions/chesscom/`:

- The Gradle plugin compiles it to DEX (`extensions/chesscom.mpe`) and the patches build
  bundles that file into the `.mpp`. `extensions/chesscom/build.gradle.kts` declares only
  `compileOnly` dependencies (Kotlin stdlib, `androidx.annotation`): those classes are
  provided by the target app at runtime and must never be bundled.
- Patches reference extension classes by exact descriptor, via `Extensions.kt` /
  `Constants.kt` (e.g. `Ldev/hyzor/extension/chesscom/Utils;`). If you rename a class or
  method, the smali reference must be updated at the same time.
- `AndroidManifest.xml` in the extension declares the permissions the extension uses so
  lint checks against them; the manifest is merged into the patched app.
- The extension supports API 23 minimum. Keep new code compatible with that.
- Keep the split thin-patch / fat-extension: a patch should be a hook plus a few
  instructions; logic, UI and storage belong in the extension.

The chess.com extension gets its context from a single hook inserted into
`MainApplication.onCreate()` (`extensionHookPatch`), which calls
`Utils.onApplicationCreate()`. That registers activity lifecycle callbacks, so the extension
can follow which screen is open.

### Resources and the manifest

`resourcePatch` decodes resources with ARSCLib. Typical operations in this repo:

```kotlin
document("res/values/strings.xml").use { doc -> /* edit XML */ }
get("res/drawable/icon.xml").writeText(...)
document("AndroidManifest.xml").use { doc -> /* add an activity, rename the package */ }
```

Files in `patches/src/main/resources/` are bundled into the `.mpp`; a patch reads them from
its own classloader (`javaClass.classLoader.getResourceAsStream(...)`) and writes them into
the app (`get("res/…")` returns the APK-side file). The chess.com Lichess badge drawables
are copied this way; the settings icon is written from a Kotlin string constant.

### In-app settings

The chess.com bundle has a settings screen inside the app. The pattern:

1. A resource patch adds `MorpheSettingsActivity` to the manifest and its title/icon.
2. A bytecode patch inserts a `NOAM_PATCHES` entry into the More tab.
3. Each feature has a marker method in `Features`; the feature's patch calls
   `markFeaturePatched(...)`, which makes the marker return `true`.
4. The settings screen lists only features whose marker returns `true`, storing toggles in
   the `morphe_chesscom` SharedPreferences file.

If you add a chess.com feature, add its marker, page and settings plumbing in the extension
at the same time, or the feature will silently have no switch.

### Signing, and what it breaks

Morphe signs the output with its own key. Consequences you will meet:

- The stock app must be uninstalled (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) unless the
  installed build was already signed with the same Morphe key.
- Play Integrity and similar attestation fail. Duolingo's *Disable login integrity* patch
  exists because email login is rejected otherwise; it is a dependency of every other
  Duolingo patch.
- Signature checks inside an app fail: Sleep as Android's `isOurSignature` tamper flag is
  cleared by its patch, and the paid `com.urbandroid.sleep.full.key` unlocker can no longer
  match the package signature.
- Server-side state is never changed. Every patch in this repo is client-side only.

## Making changes

### Adding a patch

1. Branch from `dev`, using a scoped name (`feat/chesscom-…`, `fix/duolingo-…`).
2. Decompile the target APK (jadx is fine) and find the method to change.
3. Add a fingerprint to the feature's `Fingerprints.kt` and the patch to
   `<app>/<feature>/`, or create a new feature package following the existing layout.
4. Declare `compatibleWith(Constants.…)`, `dependsOn(...)` for shared infrastructure, and
   `extendWith(...)` if the extension is involved.
5. Use the naming rules: a patch is named after what it does (`No ads`, `Enable Premium`),
   descriptions are third person, present tense and end with a period. `default = true` only
   when most users want the patch and it is safe to apply; otherwise default off.
6. Fail with an actionable `PatchException` (name the class/method/resource and the likely
   fix), not a bare cast error.
7. Build, apply with `--validate`, and test on a phone (below).
8. If the change is user-visible, update the app's page under `docs/apps/`, and the
   supported-versions table at the top of the README when a version changes.

### Supporting a new app version

1. Run `python3 tools/verify_fingerprints.py new.apk` and note every `MISS`.
2. Re-resolve the broken fingerprints against the new APK; update `Fingerprints.kt` and its
   comments.
3. Update the app's `shared/Constants.kt`: version string, `versionCode` where known, and
   `apkFileType`. (`ApkFileType` is part of `Compatibility`; Sleep as Android currently
   declares `APK` only — adding an APKM target needs a second `Compatibility`.)
4. Update the `TARGETS` in `tools/verify_fingerprints.py` so the next check covers the new
   version.
5. Build, apply to the new APK, and run the device checks.
6. Update the supported-versions table at the top of the README and the app page in
   `docs/apps/`.
7. Commit with `bump(<app>): support <version>` — `bump:` maps to the release's
   “Updated App Support” section. Keep older targets working unless you deliberately drop
   them.

Never bump a version in `Constants.kt` before the fingerprints are verified: Morphe will
show the version as compatible while the patch fails or patches the wrong method.

## Testing on a phone

This is the only real verification for a patch: the build proves it compiles, not that the
app behaves.

### 1. Build and apply

```bash
./gradlew :patches:buildAndroid
```

Add `patches/build/libs/patches-<version>.mpp` to Morphe as a local bundle/source, choose
the stock APK/APKM/XAPK for the target version, and select the patches to test. If you use
Morphe's CLI, pass `--validate`: every fingerprint must match exactly once, which catches
ambiguous fingerprints before install. Morphe writes a patched, re-signed APK.

### 2. Install

```bash
adb devices
adb shell dumpsys package com.chess | grep -E "versionName|versionCode"
adb install -r patched.apk        # same signer as the installed build: keeps data
adb install patched.apk           # different signer: after uninstalling the stock app
adb uninstall com.chess
```

- Keep the same Morphe installation/key between test rounds, otherwise `-r` updates stop
  working and you lose app data.
- Back up first. `adb backup` is unreliable on modern Android; prefer the app's own export,
  a root-level backup, or a throwaway test account.
- If the output is split APKs, install all of them with `adb install-multiple`.

### 3. Smoke test and logs

```bash
adb logcat -c
adb shell am force-stop com.chess
adb shell monkey -p com.chess -c android.intent.category.LAUNCHER 1
adb logcat -d | grep -iE "FATAL EXCEPTION|AndroidRuntime|MorpheChessCom"
```

Expect: cold start without a fatal exception, the app still signed in when the signer was
unchanged, and the patched surfaces reachable. Take a screenshot of each result you will
claim in the PR.

### 4. Per-app checks

| App | What to verify |
|---|---|
| Sleep as Android | Premium surfaces unlocked; no unknown-signature warning; Cloud Premium patch only when selected. |
| SnoreLab | Grant microphone first (`adb shell pm grant com.snorelab.app android.permission.RECORD_AUDIO`); start and stop a session; a premium-only soundscape plays without the purchase screen; Trends has no upgrade banner; Subscription page reports Premium. |
| NYT Games | Me → Settings reports a Games subscriber; archive opens; bonus puzzle is playable; AMOLED screens are black while WebView games stay dark grey. |
| Chess.com | Noam's Patches row appears; only selected patches are listed; ads gone; Arrows draws on the board; Stockfish analyses offline (after the patch-time download); optionally clone installs as `com.chess.noam` alongside the stock app. |
| Duolingo | Fresh install + email login works; Super Dashboard and profile badge; debug options open; one launcher icon; RampUp timer only if the account has a challenge. |

Record what was **not** exercised (e.g. “MAX variant applied but not installed”, “RampUp
verified in the patched DEX, account has no challenge”). Be explicit about static-only
verification — it is better than claiming a UI check you did not do.

### 5. When the UI cannot reach the feature

Some things cannot be triggered on a test account. Pull the patched APK and check the
bytecode instead (`jadx`, `baksmali`, or `dexdump`), and say in the PR that it was verified
statically. `tools/verify_fingerprints.py` on the stock APK plus a `--validate` apply covers
the “did the hook land” half.

### 6. Cleanup

```bash
adb uninstall com.chess
```

Reinstall the stock build, re-grant runtime permissions (reinstalling resets them), and
force-stop the app so the next test starts cold.

## Conventions

- Kotlin official style; ktlint settings live in `.editorconfig`.
- Public patch properties are discovered reflectively, so keep `@Suppress("unused")`.
- Put descriptor strings and version constants in the app's `shared/Constants.kt`; don't
  scatter `L…;` literals.
- Keep patches small and let the extension hold logic. A patch that rewrites whole methods
  is a smell.
- Document the *why* in KDoc above non-obvious patches and fingerprints; the README table
  only shows the user-facing description.
- Add GPLv3-compatible attribution when porting: file header (see the chess.com clone
  patch), `NOTICE`, and the README credits.
- Don't commit APKs, signing keys, tokens, `node_modules/`, or `.tmp/`.
- Don't hand-edit generated files: `patches-list.json`, `patches-bundle.json`, the README
  block between `<!-- PATCHES_START … -->` and `<!-- PATCHES_END -->`, or `CHANGELOG.md`
  (all produced by the release CI).
- The README table of supported apps *is* hand-maintained; update it when versions change.

## Git and releases

- Work on `dev` (or a feature branch that merges into it). `main` is stable.
- Conventional commits drive semantic-release:
  `fix` → patch, `feat` → minor, `perf` → patch, `bump` → “Updated App Support”,
  `build` with scope `Needs bump` → patch, `chore`/`docs`/`ci` → no release.
- Scopes used here: `chesscom`, `duolingo`, `nytgames`, `sleep`, `snorelab`.
- Pushing to `dev` publishes a pre-release (`vX.Y.Z-dev.N`); pushing to `main` publishes a
  stable release. Merge `dev` into `main` with a merge commit — don't squash, the history is
  what semantic-release reads.
- The release job runs `gradle-semantic-release-plugin`, regenerates `patches-list.json`, the
  README patch block and `patches-bundle.json`, commits them with `[skip ci]`, publishes the
  bundle and attests it, then backmerges `main` into `dev`.
- Repository setting required: *Allow GitHub Actions to create and approve pull requests*
  (Settings → Actions → General → Workflow permissions), or the `dev` → `main` PR job fails.

## Things that bite

- **Missing GitHub token:** the build fails while resolving `app.morphe.patches`, even
  though the package is public.
- **Ambiguous fingerprints:** a duplicate match is only an error under `--validate`;
  without it the first match wins silently.
- **Don't make a class mutable just to read it:** `mutableClassDefBy` inside
  `classDefForEach` converts every class in the app, and each converted class is recompiled
  into a new DEX file before the APK is written. On Chess.com (87,519 classes) that made the
  default patch set need 4.7 GB and fail at a 1.5 GB heap. Scan `classDef.methods` first,
  collect the matches, then make only the classes that get a hook mutable
  (`CustomTabsPatch` and `LichessPuzzlesPatch` do this).
- **Version string mismatch:** Morphe matches the target's `versionName`. Sleep as Android
  has no build suffix; Chess.com includes `-googleplay`. A typo makes Morphe show the target
  while every fingerprint fails.
- **`ApkFileType` is part of compatibility:** one `Compatibility` cannot cover both APK and
  APKM. Sleep as Android is APK-only today.
- **Extension refactors break smali:** renaming an extension class/method without updating
  the `L…;` descriptor fails at patch time (or worse, at runtime).
- **WebViews are out of reach:** NYT Games' puzzles are web content; no resource or bytecode
  patch reaches them. Don't promise colour changes there.
- **Stockfish patch:** needs internet, is arm64-only, downloads ~80 MB, and caches the
  verified engine in the system temp directory.
- **Clone Chess.com:** changes the package to `com.chess.noam`; test it as a separate app,
  not as an update.
- **Permissions reset on reinstall** (SnoreLab's microphone is the common one).
- **Server-side limits stay:** every patch here changes the client only; never describe one
  as unlocking a server entitlement.
- **`.tmp/` is the working directory, not a dumping ground:** one folder per app
  (`.tmp/<app>/`), and stock APKs, patched APKs and logs all go there, never in the
  repository root. It is gitignored and may contain stale experiments.
