# 2026-11-10 共有NGの通信タイムアウト

## 確認した問題

端末の版・エラー全文は未取得です。現行配信先への読み取りではHTTP200、revision416、3,853条件、1,732,184bytesを約5秒で取得できました。利用者の端末で起きたタイムアウト自体は再現できていません。

既存のアプリは接続10秒・読み取り15秒でした。一方、GASは配信キャッシュがない場合に審査・集約を実行し、スクリプトロック待機だけでも最大15秒です。さらに転送と大きな応答の受信があり、混雑や回線遅延で失敗する余地があります。

## 修正

共通の共有NG通信を `SharedNgHttp` に分離し、接続15秒・読み取り60秒へ変更。受信GETがSocketTimeoutExceptionになった場合だけ1回再試行し、転送・再試行・読み取りの間で同じ90秒の時間予算を確認します。各読み取り前に残り時間に合わせて待機設定を短くします。

元の要求がPOSTの場合は、応答を失ってもサーバーでは受理済みの可能性があるため、転送後のGETで失敗した場合も含め、要求を自動再送しません。既存のoperationIdと送信待ちキューによる後日の再試行は継続します。

HTTPSと許可ホスト、4MiB応答上限、最大3接続の転送制限、JSONの成功確認を維持。接続先URL・条件・レポーター情報を新たにログへ出しません。エラー文はタイムアウト・保存済み条件の保持・再同期の案内を日本語で表示します。条件の適用・審査・レポーター除外の仕様変更はありません。GASソースとデプロイは変更していません。

その他、20秒相当のサーバー処理、GASのPOST→GET転送と本文保持、GETのみ1回の再試行、POSTとその転送応答の再送禁止、90秒予算の消費、滴下応答、切断、許可外転送、転送ループ、4MiB超過、HTTP503を確認しました。

## 途中の失敗と制限

初回の背景状態の試験はUnknownHostExceptionでした。AndroidのLog.getStackTraceStringはこの例外を空文字にするため、試験側をStringWriterへ変更して原因を記録しました。手動同期に合わせてアプリを前面へ出すよう試験を変更しています。DNSエラーが利用者のタイムアウトと同じ原因だとは断定していません。

初回の前面試験では配信のok/full判定が失敗しましたが、その時点の試験が応答のerrorを記録しておらず、詳細は不明です。診断を追加した再確認は同じ製品で3,853条件/10,897msの成功、その後の最終3版も上表の通り成功しました。最初の失敗を成功数へ含めず、サービス側の瞬間的な失敗原因を特定済みとは扱いません。

試験APKの初回パッケージにはホスト試験のクラスが入りD8がJDK用HttpServerの警告を出しました。Android試験クラスだけの別出力先に変更して、導入前に再生成しました。エミュレータの冷間起動ではSystem UI応答停止があり、XMLでSystem UIとWaitボタンを確認して復帰。製品クラッシュとは区別します。

利用者のプレ公開指示に従い、検証した共通修正を既存Semantic Release CIへ送ります。GASの審査・配信ルールとデプロイは変更しません。
