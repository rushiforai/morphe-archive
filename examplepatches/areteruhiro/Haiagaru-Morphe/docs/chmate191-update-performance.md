# 191 dev / 226 dev 更新処理の比較

検証日: 2026-10-17。対象は公式の 0.8.10.191 dev / 0.8.10.226 dev APK の DEX と、パッチ済みの検証アプリ。
報告された「すべての板で更新進捗が途中停止する」症状は、エミュレータでは再現していない。原因確定・解消確認とは扱わない。

## 確認結果

| 項目 | 191 / 226 の結果 |
| --- | --- |
| 共通クライアントの接続・読み込み・書き込み上限 | 両方とも各15秒 |
| プロトコル | 両方とも HTTP/1.1 を指定 |
| 更新ワーカーの共有プール | 両方とも core=5 / max=128 / queue=10 / keepAlive=1秒 |
| 板取得キャンセル | 両方とも native Call.cancel → キャンセルフラグ → FutureTask.cancel(false) |
| 進捗の画面反映 | 両方とも保留値を上書きし、未処理通知がある場合は新しい Runnable を追加しない LiveData 型の方式 |
| DNS の標準実装 | 両方とも InetAddress.getAllByName。OS の DNS 処理そのものは置換されていない |
| 接続再利用 | 親から派生するクライアントでプールを共有。標準アイドル上限5本・保持5分 |
| 標準 subject 解析 | 主な手順は同じ。板種別・文字コードの取得方法などは異なる |
| DAT 読み書き | 両方ともコピー用2048バイト・出力用8192バイト |
| 接続候補へのフォールバック | **差あり**。191は従来の逐次方式。226には250ms間隔で別の候補を開始する競合接続方式があり、既存検証アプリのクライアントでも有効 |

### 有力な追加調査候補

191 の逐次接続では、先に選ばれた IP/経路が応答しないと、その試行の失敗まで次の候補へ進めない。
226 の競合接続はこの待ちを短縮できる可能性がある。IPv4/IPv6 の片側や特定経路が不調な環境における版間差の候補である。
ただし、報告端末の失敗経路・DNS結果・接続タイミングは未取得であり、今回の原因とは断定していない。
DNS解決自体の停止や、レスポンス本文の受信停止を、この方式だけで解消できるわけではない。

## ローカルで既に実装した予防策

191のみ: 中間進捗の通知を100ms間隔にまとめる設定、および板・スレGET限定の通信全体上限を追加。
上限は標準0（元の動作）、選択肢30/60/120秒。POST、画像、動画は対象外。
これらは接続並列化とは独立した予防策。今回追加した250ms TCP競合接続は末尾に記載。

- 純Javaの進捗ゲート: 15チェック成功。
- 191 native経路のローカル受信テスト: 17チェック成功。
- 4096バイトの受信と最終進捗を維持し、4バイト刻み読み取り時の通知は1025回から10回へ削減（計測値）。
- 既存の短い上限2秒を維持し、連続受信中の中断は2171ms、その後のGETも成功。
- 通常のエミュレータ更新では大量の進捗通知は観測しておらず、通知軽量化を実障害の解決とは扱わない。

## 191への250ms TCP競合接続の追加実装

`TcpConnectRace` と `NativeUpdatePolicyPatch` を追加し、191の既存接続探索へ組み込んだ。
Haiagaru設定の詳細設定にある「191の代替IPへの切り替えを速くする」でオン／オフ可能（初期オン）。
設定の保存・再表示・元の値への復元を検証用191アプリで確認した。

- 標準の板・スレ取得GET、直接接続、複数の解決済みIPがある場合だけ対象。
- 最初のTCP接続を即開始し、未完了なら約250msごとに次の候補も開始する。即失敗時は待たずに次へ進む。
- 成功した実ソケットをnative接続へ渡し、HTTP要求・TLS処理は既存処理を使う。未採用ソケットは閉じる。
- 各接続の元の15秒上限は維持。投稿・画像・動画・プロキシ通信は対象外。
- 同時実行はプロセス全体で最大8試行。予算不足時は元の接続処理に戻る。
- 呼び出しキャンセルで試行を閉じる。未受領ソケットには5秒の回収処理を設ける。
- DNS解決、TLSやHTTP応答自体の無応答を0.29秒で解決する機能ではない。

純Java試験 `VerifyTcpConnectRace` は20チェック成功。ローカル実ソケット試験は
`frida-update-race191-test.js` でオン／オフ・正常先頭・画像除外・単一候補・証明書拒否・キャンセルを検証し8/8成功。
FridaがJava例外を `Error: <例外クラス>: ...` として返すケースに合わせてテストの型判定を修正した。
証明書検証を無効化して通したものではない。

前面状態を確認して再起動後に測定したログは `network191-race-policy-foreground.log`。
先頭候補無応答時はオン527ms（初回）、318ms（次回）、オフ15077ms。
2回目は最初のTCP開始22ms、次候補開始283ms、正常候補接続完了285ms、本文取得完了318ms。
他の測定ではオン344～510ms、初回初期化を含む試行は1292ms。
226の比較値282～290msに近い切り替えを目指す実装だが、0.29秒固定や実回線の速度は保証しない。
Frida再接続中にART/Fridaのnativeスタックで起きたSIGSEGVは完了試験と分離し、新しいプロセスで測り直した。

生成済みローカルバンドル: `patches/build/libs/patches-1.8.7.mpp`。
検証APK: `build/verification/network191-fallback-optimized.apk`（独立パッケージ）。
コミット・リリース公開はしていない。報告端末の実際の停止原因の確定・解消確認も未実施。
最終試験は8/8成功（証明書拒否335ms、キャンセル56ms）。試験用DROPルール2件と
16881/16883のADB reverseを削除し、OUTPUTが元の4つのシステムチェーンだけであることを確認。

## 2026-10-27: 再利用接続が無応答になる場合の対策

過去の会話と上記の検証を再確認。先頭IP無応答の対策は既に存在し、標準15秒の接続/TLS/ヘッダー/本文タイムアウトも既に検証済みだった。今回の報告は巡回・スレ取得のみ停止、機内モードで一時復旧、226では未報告。報告回線そのものの停止時スタックは未取得であり、原因は断定しない。

新しいローカル条件として、HTTP/1.1で初回だけ正常応答し、同じTCP接続の2回目以降は無応答にした。191 native clientでは初回521ms成功、再利用時15037msでSocketTimeoutException、その後の新規接続543ms成功。Connection: closeを付けると3回とも別ソケットになり544/566/555msで成功。`scripts/network191-reuse/`、`build/network191-reuse-baseline2.log`。これは特定の接続経路の劣化を模擬した結果であり、191だけに起きる現象と証明したものではない。

この条件への対策として、191の既存getLabel reader内15個のexecute前フックに限って、対象GETのConnectionをcloseにする設定を追加。設定名は「191の板・スレ取得で接続を再利用しない」。利用者の明示指定で初期オン、明示オフは尊重する。HTTPエンジン/TLS検証/接続先/投稿/Cookie保存は維持。板・スレ以外の画像/GIF/動画、POSTは対象外。元Request/Headersは変更せず、URL/メソッド/本文/tags/他ヘッダーを引き継いだCall専用Requestへ置換する。既に待機中のCallの強制停止やプール全破棄はしない。OFFは次の取得から従来の再利用方式へ戻る。

通信全体の上限設定0/30/60/120秒は既存仕様のまま、初期0を維持。接続を毎回作るため、待ち時間/通信量/電池消費が増える可能性がある。設定内にも記載。設定共有・プリセットの既定値も登録。hostのヘッダー不変性/スコープ14項目成功。最終APKの生成・native bridge・初期ON/明示OFF・スコープ・ローカル再現条件の再検証は実施中。
検証追記: 最終候補通常LintVital付きbuild/network191-fresh-final-build.log成功3m4s。初回再buildはC1 CodeCache不足でpackageRelease停止、ReservedCodeCacheSize256mへ増やして成功（チェック無効化なし）。15execute位置/bridge引数/既存timeout保持検査、native runtimeの初期ON/明示OFF/GET POST mediaスコープ/Request不変性16項目成功。設定実Switchの保存・復元成功。無応答再利用は15013ms失敗、対策ONでは3回527/80/60ms成功。191混在media24項目も成功し312ms cancel、各GIF1取得。記録build/network191-reuse-final-runtime.log / network191-reuse-settings.log / network191-media-final-runtime.log。Part3本文表示・新規crash空を確認、実回線の長期巡回停止自体は未再現。

補足: Connection: closeは対象の取得が使い終えた接続をプールへ戻さない方式。別の画像取得等が既に共有プールへ戻した接続まで強制破棄するものではなく、最初に既存接続を使用する可能性は残る。通信中の画像や投稿へ影響させないため、共有プールの一括破棄は採用しない。
