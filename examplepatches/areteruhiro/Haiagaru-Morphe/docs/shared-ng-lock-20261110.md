# 2026-11-10 共有NGのGASロック競合

利用者の追加エラー全文がGASの「ロックのタイムアウト」であったため、dev.21のHTTP待機時間延長とは別にサーバー側を修正しました。初めの通信タイムアウト対策だけではこのエラーを解消できません。

## 原因と修正

実行履歴では毎分のreviewPersonalNgが数十秒〜253秒かかり、360秒の実行上限で終了した記録もありました。配信キャッシュが切れると読み取り側も審査・集約のロックを待ち、待機者がキャッシュを再確認せず同じ処理を繰り返す構造でした。

- 配信のロック取得後にキャッシュを再確認。生成とキャッシュのコミットを同じロック内で完了し、待機者の重複生成を防ぎます。
- キャッシュ片はgetAll/putAllでまとめて転送。全片が揃いハッシュが一致したデータだけを使う方式と、マニフェストを最後に書く方式は維持します。
- 毎分審査はロックが使用中なら短時間で終了し、重複した審査をキューへ積みません。審査完了時に同じ行データから配信キャッシュを生成し、再度のシート全件読み取りを避けます。
- 管理用の出力・GitHub配信でも、外部通信より前にキャッシュを用意します。
- 管理用復元フラグの確認を対象者ごとのProperties RPCからキー集合の参照へ変更しました。通常の登録内容・審査・票数・除外の扱いを変更する意図はありません。

## 検証・反映

Nodeのロック競合61項目と、既存の個人NG148・ライフサイクル116・フィードバック65・サービス41・審査53・Edgeレベル19・旧プロトタイプ13項目、計516項目が成功。ロック待機中の他実行のキャッシュ生成、ロック取得失敗直後の生成、生成失敗、破損片、Unicode分割、マニフェスト未コミット、審査の重複起動、審査済み行の再利用、権限を持たないロック解放の禁止を検査しました。

既存Apps ScriptのPublish.gsがローカルの修正前ソースと一致することを確認してから保存しました。最初のversion18では、重複した審査自体がロックを占有し続け、2並列GETとも約27秒で更新中エラーになりました。その後、実行履歴から毎分審査の問題を特定し、PersonalInbox.gsも修正。既存サーバーとローカルの修正前PersonalInbox.gsの一致を確認し、両ファイルを検証済みソースと一致させました。

既存デプロイIDを維持して**GAS version19（2026-11-10 22:21 JST）**へ更新しました。実行ユーザー・アクセス権は変更していません。更新直後は既存実行によるロック競合が残りましたが、その後の同じ/execへのGETはHTTP200・ok=true・revision422・3,873条件を7.515秒で返しました。エビデンスはbuild/shared-ng-lock-20261110/live-v19-later.json、更新画面はdeployed-v19.jpgです。公開条件や個人識別子の実値を新たなログへ出していません。

本変更はサーバーへ反映済みであり、MPPの更新は必要ありません。長時間の稼働やすべての混雑状況まで確認済みとは扱いません。エミュレータ確認は利用者の指示で実施しません。
