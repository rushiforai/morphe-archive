# 191の未取得5chスレ表示速度の調査

利用者報告は「1.18.2より1.18.3で未取得スレを開く反応が遅い」。タップ前後のどの段階かと対象URLは不明。実機はADB未接続で、利用者指定によりエミュレータで検証した。

## 版比較

公式1.18.2/1.18.3の公開MPPから、同じ元191 APK・パッチ選択・パッケージ・署名でAPKを作成。`emulator-5580`の隔離package `jp.co.airfront.android.a2chMate.haiagaru.migration191242`へ署名照合して上書きした。通常アプリや実機のデータは変更していない。公開MPP SHA256は1.18.2が`4d00bcc3868bf963137854eb791fd05a050d3ee92da4b73f73e29a2e54c8dba7`、1.18.3が`23c4e3c10c5765a9e2c4ee9a4d7c698a239a9204f6aeb30942d16a795b7e07ee`。

両版のソース差分に通信処理の直接変更はなかった。履歴内で利用者提供のPart4（android/1793113633）をサンプルとし、タスク開始時に未保存だったことを検査し、以後タスク所有と記録したDAT/idx/bookmarkだけを各回削除して測定した。各回プロセスも再起動した。FridaでActivity生成・復帰、191のnative Call応答ヘッダー、最初のレスを持つAdapter、100ms周期のmain Handler間隔を記録した。Adapterの確認は最終画面描画完了と同義ではなく、native Callの時間も先行する過去ログimporterを含む通信全体の時間ではない。

|版・試行|要求から最初のレス確認|native応答ヘッダー|main tick最大間隔|
|---|---:|---:|---:|
|1.18.2 初回|6,843ms|466ms|3,108ms|
|1.18.3 初回|8,692ms|469ms|5,101ms|
|1.18.3 再測定|9,422ms|455ms|4,775ms|

投稿数も469→472→473と増加し、エミュレータのSystem UI応答停止もあった。Aを再測定するとBより遅いため、これだけで1.18.3固有の回帰や、今回の変更によるスレ全体の改善率を断定しない。生データは`build/thread-open-real*.json`。最初のPC urllib試験は403だったが、アプリではDATとレスを取得できた。PCの403をアプリでの取得失敗とは扱わない。

## 確認した重い処理と修正

mainスレッドのサンプルで`Haiagaru.defaultAdClass → classExists → Class.forName → DexPathList.toString`を複数回確認した。191では243/242/241用の組み込みクラスが見つからず、画面内の各ビュー・各再確認で検索失敗と例外生成を繰り返していた。この処理は1.18.2にも存在する。

- 組み込み広告クラスの選択を、インストール済みAPKのプロセス内で一度だけ行う。
- 一回のビュー走査では広告クラス設定を一度だけ読み、子へ同じ値を渡す。
- 各走査の開始時には設定を再読込するため、任意の広告クラス設定変更は次の走査で反映する。既存の一致判定・画面コンテナ保護・広告折り畳み処理は維持する。

隔離された201ビューの走査は修正前約248〜489ms、修正後191で0.40〜0.46ms、226で0.35〜0.58ms、242で0.30〜0.42ms。異なる計測時点の範囲であり、スレ起動全体の倍率として使わない。`scripts/ad-walk-runtime.js`は非表示にすべきでないビュー、4つの組み込み既定値移行、任意のクラス名維持、対象変更後の反映を各版10項目で確認し、設定をfinallyで元に戻す。

## 最終検証・状態

最初のビルドはPC側JVM native memory allocation失敗。タスクのAVDをデータ保持で停止してから通常Lint/R8ビルドを再実施し、2分43秒で成功した。MPPは`build/thread-open-ad-cache.mpp`、SHA256 `7f39bcc7e0ab49dc6e4e11f97854c20198fd2c0652fb94e6719f599d75c70711`。

191/226/242へ署名一致install-r・起動、各広告走査10項目、各画像/GIF/拡大8項目、nativeスレ本文を確認。191の実DATは前記のレスを取得、最終の通常本文スモークは合成スレのレス45を表示。242の最初のUI dumpがnullだったため再表示・新規dumpで確認した。画像試験の最初の失敗時にはSystem UI応答停止ダイアログがあり、待機と今回起動したMorphe終了後に再試験して成功。失敗を成功に数えない。最終アプリcrash buffer空、native bytecodeフックのレジスター・元命令変更なし。

作成した公開スレのDAT/idx/bookmark、対応する論理位置ファイル、所有markerを検証後に削除。他のスレや通常アプリのデータ、投稿・NG登録・共有NG送信・GASは変更していない。詳細は`build/thread-open-cache-cleanup.json`、`thread-open-position-cleanup.json`、`thread-open-ad-walk-after*.json`、`thread-open-image*.log`、`thread-open-ad-cache-final-crash.log`と導入台帳。

修正は未公開。確定した広告確認処理の効率化を実装した段階であり、利用者報告と同条件の1.18.3固有の速度差は継続確認が必要。

## 2026-11-03 利用者提供GIFによる1.12.0-dev.1 / 1.19.0比較

上記の広告クラス確認最適化は1.19.0へ公開済み。ただし利用者から同じ191 dev / Samsung SM-S948Q / Android17で遅延が残る動画が提供された。旧 https://i.imgur.com/QuRrmef.gif 、新 https://i.imgur.com/nBZ3N63.gif 。GIFのデコードフレームと各フレームのdurationを集計した。見えているのはタブレット形式の板一覧からAdGuard Part104を開く操作で、読み込み中画面のURLも同じスレを示している。

主に増えているのは板一覧が残る区間。これまでのResListActivity直接起動による計測だけでは、タブレットの板一覧クリック経路や、既存スレからの切り替え前処理を十分に含めていない。今後はnative一覧クリック→旧画面のpause/save→新画面作成→通信/描画を区別する必要がある。候補の一つとして、追加のReadingPosition保存はnative onPauseにフックされ、AtomicFile.finishWriteまで同期実行しているが、この動画だけで原因と扱わない。

1.19.0で廃止した39か所の全クラス走査はパッチ適用時の対象探索。アプリ内のスレ表示前処理とは別なので、走査廃止や全定義一致をこの遅延の解消確認として扱わない。検査用データ `build/thread-open-gifs-20261103/comparison.json` / `old-frames.json` / `new-frames.json` / contact PNG。動画の取得はフレーム分析用であり、GIF全長の差を表示速度差として数えていない。
