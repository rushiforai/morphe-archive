# UI変更時のテーマ適用

- 新規画面・ダイアログ・表示部品を追加する場合は、まず `porting/original-to-mod.patch` の `MyThemeMaterialYou`、`DynamicTheme.apply` と `DynamicTheme` の既存補助メソッドを確認する。
- Activity は既存の `DynamicTheme.apply` の適用タイミングを維持する。Material You 設定がオンかつ Android 12 以降の場合、`res/values-v31/styles.xml` と `res/values-night-v31/styles.xml` のテーマ色を利用する。
- コードで生成する進捗表示やアイコンには、生成した View の Context の Theme から `colorAccent` (0x7f03005e) を解決し、その色を明示的に適用する。固定色・システム既定色に任せない。設定がオフのときは従来テーマの同じ属性を使う。`porting/pull-refresh.patch` の `SwipeRefreshLayout.setColorSchemeColors` が実例。
- 新規 UI は Material You のオン・オフ、および明暗の双方で色とコントラストを確認する。

- ダイアログは `UiDialogs.builder(context)` で生成し、ポップアップには `UiTheme191.context(context)` を使う。独自入力部品は `nicoid-managed-input` として既定の下線・余白の上書きを避ける。
- ダイアログ・入力フォーム・操作一覧は `UiDialogs` の共通配色を使う。標準テーマ由来の紫色を入力文字・ヒント・下線・カーソル・ボタン・スライダーに残さず、実際の Activity のテーマ色を適用する。

# 更新内容の記載

- README は利用方法・機能説明を中心にし、Issue 番号やリンク、バグ修正履歴は記載しない。
- リリース本文と CHANGELOG は英語で記載し、対応した Issue は文末の ` (#xx)` にリンクを付ける。

# 公開文面

- 非公開の仕掛けについて、README・リリースノート・コミット名・ワークフローの表示名・ログに具体的な内容を書かない。関連する検証の表示名は一般的な表記にする。

# フラットな共通デザイン

- 装飾目的の影・グラデーション・Elevationを追加しない。共通の `FlatUi191` とテーマリソースを使う。
- Z順序、ダイアログ／ポップアップの前面表示、ドラッグ中の状態は維持し、影だけを除去する。動画／サムネイル本来のピクセルや動画上の可読性用の効果は変更しない。
- 動画情報の既存タグ一覧は共通の `NicoidFlatTag` スタイルと明暗の `nicoid_tag_item_*` カラーを使い、項目間だけ4dp空ける。

- 旧UI画像はリソースIDと寸法だけでなく、BitmapFactory・BitmapDrawableキャストなど読み込み側の形式要件を維持する。呼び出し元を変更・検証しない限り、PNGをXMLへ置き換えない。配布MPPの全PNG形式・密度パス・寸法を `VerifyLegacyImageFormats191.py` で確認する。

# 動画リストの共通表示

- 既存Adapterの動画行は `VideoRows191` で表示を整え、画面ごとの同じ日時・文字サイズ・余白処理を追加しない。既存のView ID、タイトルの行数制限、クリックと長押しの経路を維持する。
- 先頭は画面で重要な日時（投稿・登録・視聴）、補助日時は統計情報の下に置く。日時は `yyyy/MM/dd HH:mm` と意味のラベルを使い、不明な投稿日時を登録日時から作らない。
- 取得できる統計は再生・コメント・いいね・マイリストの順。キャッシュ状態、視聴回数、マイリストのメモなどの固有情報を共通化によって削除しない。

- 順位は従来の大きなオーバーレイ表示を維持する。順位用の独立した横幅を確保せず、テキスト列の右端には4dpだけ余白を付ける。

# リリース運用

- 正式版の公開、dev公開、既存リリースの再公開・本文変更は、必ずユーザーから明示的に許可されたときだけ行う。通常のビルド、デバッグ、main/devへの変更を公開許可と解釈しない。
- 公開済みのリリースタグは移動・強制更新・削除しない。既存リリースのMPPやZIP/tar.gzを上書きしない。修正は新しいバージョンとして検証し、承認を得て配布する。
- v1.10.1の実装基準は porting/revisions/v1.10.1 内の復元Smaliソースであり、以前のJavaスナップショットは履歴資料である。古いJavaだけを編集しても配布ペイロードに反映されないため、ビルド入力の所有関係を必ず確認する。
- 公開済みv1.10.1のソースフォルダーは変更しない。新しい実装は次版用に分離し、差分のビルド・回帰検証を行う。
- main/devは直近の正式版と整合させ、パッチバージョン、patches-list.json、patches-bundle.jsonと生成されたMPPを照合する。
- リリースのActions実行は手動かつ明示的な確認入力を必須とする。通常のpushでは検証のみ行う。
- GitHubのタグ保護・ルールセットは、管理画面で変更制限を有効化する（CIの手動実行制限だけではタグ改変を防止できない）。

- リリース用の Pull Request は作成しない。ユーザーがリリースを指示した場合は、必要な検証後に main へ直接反映して既存のリリース処理を実行する。
- dev から main へのリリース用 PR も自動作成しない。

- PR 本文・README・リリースノートなどの公開向け説明には、利用者向けの変更内容のみを記載する。会話上の確認経緯、検証手順・件数、実装の復元方法やビルド内部の作業過程は記載しない。
