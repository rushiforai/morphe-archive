# Galaxy XR USB streaming investigation — 2026-09-16

**Scope clarification:** this record proves manually configured USB transport. It does not establish Quest-style automatic setup. The later [feasibility investigation](QUEST-PARITY-2026-09-16.md) records the NCM failure and final restored `mtp,adb` state; the RNDIS-enabled state described below belongs to the earlier successful streaming session.

The separate automatic RNDIS experiment was retired at the user's request on 2026-09-19; it did not implement Quest-equivalent NCM. This historical manual streaming evidence remains valid independently of that removed patch.

## Scope and result

The user requested USB support for Steam Link `2.0.23/5002363` and connected a Galaxy XR for diagnosis. **USB streaming was live-verified with the existing installed APK.** Android RNDIS, the Windows RNDIS6 driver, and a temporary local-only Windows IPv4 address enabled the link. During a 12-second Wi-Fi-off trial, USB continued receiving substantial traffic while Wi-Fi counters remained unchanged. The user separately confirmed that the SteamVR image kept updating and head tracking remained responsive.

The earlier static conclusion needs qualification: the Quest-only checks gate the shell's automatic NCM setup and USB indicator, not all streaming over a manually configured USB IP network. See [native audit](NATIVE-5002363.md). Do not add a renderer patch or force a connected indicator to compensate for a missing Windows adapter.

## Windows blocker

The headset's Samsung USB composite parent and ADB child are working. Its separate RNDIS child has these identifiers:

```text
USB\VID_04E8&PID_6864&RNDIS
USB\SAMSUNG_MOBILE&RNdis
USB\Vid_04E8&Pid_6864&Class_02&SubClass_02&Prot_FF
```

Windows incorrectly binds that child to `usbser.inf`, service `usbser`, class `Ports`, friendly name `USB Serial Device (COM5)`. No corresponding Windows network adapter exists. The session is not elevated, so the user was asked to select Microsoft's Remote NDIS compatible driver for this specific child. The Samsung ADB interface and composite parent must not be changed.

Microsoft documents the [Remote NDIS driver architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/remote-ndis--rndis-2). No downloaded third-party driver, unsigned INF, firewall change, network sharing change, APK installation, or SteamVR restart was performed for this checkpoint.

The built-in INF `C:\Windows\INF\netrndis.inf` contains `USB RNDIS6 Adapter` / `usbrndis6.ndi`, but marks its models `ExcludeFromSelect`. Its corresponding driver-store package contains `rndismp6.sys` and `usb80236.sys`; the binaries need not already be copied to `System32\drivers`. The user could not find the network driver through the serial-device wizard.

`Install/Repair-GalaxyXrRndisDriver.ps1 -Mode Preview` successfully enumerated the real Microsoft candidate, version `10.0.26100.9444`, section `usbrndis6.ndi`, model ID `ms_rndisusb6`. The helper uses a private single-INF global driver list inherited by the exact RNDIS child; Preview does not select or install. Composite-device input was rejected. Apply requires elevation and saves original driver information before the targeted installation. Independent source review checked the SetupAPI inheritance, driver-selection, and device-installation APIs.

The user ran Apply in an Administrator PowerShell and reported success. A fresh independent query confirmed `USB RNDIS6 Adapter`, class `Net`, `netrndis.inf`, service `usbrndis6`, status `OK`. Windows created interface `44`, alias `Local Area Connection`. Its reported link rate is `426.0 Mbps`, which does not establish negotiated USB 3 speed. The original-driver information backup is retained under `build/usb-streaming/`.

Windows-to-headset IPv6 link-local ping over interface `44` passed `3/3` with `<1 ms` replies. IPv4 remained APIPA `169.254.46.117/16`. Android NetworkStack recorded DHCP discovers from the Windows adapter and repeated offers for `192.168.231.146/24`; Windows did not obtain the lease. A targeted `ipconfig /renew` made no progress and its task-owned process was stopped.

The user ran `Set-GalaxyXrUsbHostAddress.ps1 -Mode Apply -Address 192.168.231.146` in Administrator PowerShell. Live Preview had verified the exact adapter and headset subnet. Independent readback confirmed a Preferred manual `192.168.231.146/24` address. Windows-to-headset IPv4 ping passed `3/3`, `0–1 ms`; reverse ICMP had no replies, without preventing the subsequent stream. Android's route for app UID `10253` selected `usb0`/table `97`. Ethernet retained the only Windows IPv4 default route. No gateway, DNS, firewall, or Internet Connection Sharing changes were made.

## Setup helper validation

`Install/Set-GalaxyXrUsbStreaming.ps1 -Mode Status` passed on the connected device: it confirmed Android UP/tethered state, resolved the Windows RNDIS child through the Samsung parent serial, and diagnosed the actual `usbser.inf` mismatch without reporting readiness. Android denied sysfs counter reads; the final helper reads the accessible `/proc/net/dev` counters instead. Its offline checks cover device rejection, function allowlists, subnet comparison, nonzero USB-switch exit with successful state confirmation, repeated-enable rollback preservation, and verified restoration. After driver repair, Status correctly recognized the network adapter but refused to report complete IPv4 readiness while Windows had an APIPA address.

The first live Enable check exposed Samsung's `svc usb getFunctions` writing its successful result to stderr. The helper now accepts that stream only for this command, followed by its strict function allowlist. Actual Enable → Restore → Enable passed: RNDIS and ADB returned, Restore confirmed `mtp` before removing the record, and the final Enable preserved a fresh MTP rollback record. ADB returned `255` during scripted USB switches; the verified final state was used to determine success. RNDIS is currently enabled for the pending Windows repair.

## Live streaming result

The user opened Steam Link and reported connection to SteamVR. Host logs identify SteamVR `2.17.10`. Android PID remained `13451` through the bounded test.

Relevant app log events on 2026-09-16:

```text
13:22:15.770 BTrySetupUSBNetwork: Not an Oculus headset, not attempting USB setup.
13:22:33.880 SVLDataLinkTransferUDP::Init 192.168.231.22 dev usb0 10400 0 IPv6: 0
13:22:33.880 SVLDataLinkTransferUDP SO_BINDTODEVICE 192.168.231.22 dev usb0 OK
13:22:34.180 SVLDataLinkUber: Found primary link 192.168.1.198
13:24:27.915 SVLDataLinkUber: Found primary link 192.168.231.22
```

The host independently initialized and bound port `10400` on USB address `192.168.231.146` at `13:22:30.218`. With Wi-Fi initially enabled, both interfaces carried substantial traffic. The initial “primary” log named Wi-Fi; after Wi-Fi removal, another named USB. [Later disassembly](USB-SELECTION-PLAN.md) established that this message marks the first decrypted receive and can recur when that marked transfer disappears. It does not establish transport preference or prove that USB traffic began only after Wi-Fi was disabled. A false shell USB-support flag did not prevent a working scene USB link.

A bounded script disabled headset Wi-Fi, waited 2 seconds for transition, sampled counters over **12.100 seconds**, and re-enabled Wi-Fi in `finally`. [Raw compact evidence](wifi-off-trial-2026-09-16.json):

| Interface | Received-byte increase | Transmitted-byte increase |
|---|---:|---:|
| `usb0` | 188,743,876 | 9,232,019 |
| `wlan0` | 0 | 0 |

The observed USB receive rate was approximately **125 Mbit/s** over that interval. Wi-Fi was reported disabled at both interval boundaries and the app's former connected Wi-Fi UDP socket disappeared. The USB socket had no recorded drops in those snapshots. This is a short transport check, not a maximum-throughput benchmark or proof that earlier freezing issues are resolved.

Immediately after the restore command, Wi-Fi was still asynchronously transitioning; a subsequent independent query confirmed `Wifi is enabled` and `wlan0` UP with its original IPv4 address. No Wi-Fi configuration was intentionally left disabled. In response to whether the image continued updating and head tracking remained responsive during the trial, the user answered: **“Yes, it kept working.”**

## Remaining validation and operation

1. Longer stability, higher-bitrate behavior, and cold connection with Wi-Fi already off remain untested.
2. Enable RNDIS and establish the matching Windows address before opening Steam Link. For the proven workflow, retain Wi-Fi for initial discovery; continued streaming with Wi-Fi disabled was tested separately. Exclusive USB preference with Wi-Fi enabled was not established.
3. The Windows address uses ActiveStore and can disappear after reboot. Re-run Preview and Apply only after checking the current headset subnet. Restore the host address before disabling RNDIS when rolling back.
4. No APK mutation was necessary for this successful manual USB data-path trial. The setup/driver/address tooling reproduced that manual workflow. No recommended bundle, catalog, patch default, or older exact base was changed during this trial; the later default-off automatic setup implementation has separate validation.

## Rollback and artifacts

The pre-test USB function was `mtp`; `adb shell svc usb setFunctions mtp` restores it while retaining enabled ADB. Do not change `persist.sys.usb.config` to make this experiment permanent.

No APK/native library was edited and no new APK, decoded derivative, compiler output, or native payload was generated. The installed APK was inspected in memory. Exact source APKs, decoded bases, existing diagnostics, and unrelated workspace files remain preserved. RNDIS, the working Microsoft driver, and the temporary host IPv4 address stay enabled for use; device USB-mode, original-driver, and host-address rollback records remain in ignored `build/usb-streaming/`.
