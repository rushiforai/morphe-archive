# Galaxy XR whole-view freezes: live investigation, 2026-09-15

## Finding

The capture establishes repeated disruption of Steam Link's video delivery and reset/recovery path. It does **not establish a memory leak as the cause**. A 90-second trace contains 9 decoded-output gaps longer than 50 ms, including a **1,988.761 ms gap**. Stream feedback errors, FEC recovery failures, and decoder flushes occur in the same intervals.

The root of the delayed/out-of-order feedback remains unresolved between client scheduling, transport, and host receive scheduling. The stock host reset policy amplifies a stale feedback packet into backward/forward mismatch bursts. Reset counters therefore are not counts of distinct visible freezes.

The user described brief freezes of the whole view and reported **about the same freezes during the authorized 150 Mbit/s comparison**.

## Verified running configuration

- Galaxy XR SM-I610, Android 14, Steam Link **2.0.23 / 5002363**, PID 14379 throughout the main capture; SteamVR Home, 90 Hz.
- Installed native library, DEX, manifest and config payloads match the prior audited default 6-patch bundle. The native `FlipFrame` and all 5 investigated client cadence functions remain byte-identical to stock 5002363. See [installed payload evidence](native-leak-candidate.md).
- The static Android Surface trigger helper is the expected `libgxr_ast.so`; retired experimental video-surface helpers are absent.
- USB carries ADB; streaming uses headset Wi-Fi and host Ethernet. Host initially uses fixed **400 Mbit/s**, automatic bandwidth off.
- Live custom Windows driver wraps Present. Its heavy frame-processing path reports inactive, frame counter 0. Its separate NVENC hook and API upgrade 11.1 to 12.1 are active; their causal role is untested.

It changed from 400 to 150 at **12:59:12.105 CEST** and returned to 400 at **13:01:12.105 CEST**. `automaticBandwidth=false` and `recommendedBandwidthMbit=400` were retained and verified on restoration. Neither SteamVR nor the app was restarted.

The change took effect in the running driver: `Link BW` logs report 150 and later 400. Actual adapter-wide outbound traffic was 135–137 Mbit/s during the lower-rate window and 325 Mbit/s after restoration. The 150 window still has 11 resets when its first 5 seconds are excluded.

The user's assessment was **about the same freezes**. This 1 short comparison shows that reducing bandwidth is not a sufficient fix. The lower raw reset count does not establish a reliable improvement or isolate network, decoder workload, or host behavior. The before/test/restored windows used the same running processes; the follow-up device collectors used local memory queries and no Perfetto.

The local-memory follow-up contained 0 explicit GC messages while FEC/decoder errors continued. The 180-second A/B capture also contained 0 explicit GC messages, 22 FEC unrecoverable errors, 9 queue-input errors, and 0 occurrences of the 4 stock leak-branch errors. These whole-capture counts include transition/restoration time and are not solely the 150 Mbit/s phase.

## Proven native reset path

1. Stock client `OnTopOfFrame` increments a pose-cycle ID and queues 4 pose phases. `HandleEvent` extracts that ID; `SendPoses` writes it to control-packet offset `+0x1c`.
2. The host receives this client packet through `SVLServer` packet-type 1 dispatch. Its comparison triggers a reset when the ID difference is outside `[-5, +12]`, after an early small-stale-packet filter.
3. The handler can replace its last ID with the stale arriving ID. The next current packet can then trigger another mismatch in the opposite direction.
4. The queued reset reaches the encoder as severity 1 / `Cause Mask: 000100`. This is not evidence of an independent NVENC hardware failure.
5. Device FEC failures and decoder flushes accompany large interruptions in decoded-buffer delivery. The trace's longest output gap is about 2 seconds.

Within that longest gap, the same device trace contains **18 FEC log entries and 7 decoder flushes**. This overlap does not depend on the Windows/Android clock alignment.

The IDs are **pose-cycle sequence numbers**, not the last displayed or decoded video frame. Client phases are scheduled by deadline, so small out-of-order IDs can originate before transmission. The normal phase span is 8.33 ms at 90 Hz; it does not by itself explain stale IDs 6–29 cycles behind. Packet send-time instrumentation is needed to distinguish substantially bunched client generation from later buffering/reordering.

The installed Visual Delay option adds 60,000,000 ns to the OpenXR pose-query timestamp. It does not sleep for 60 ms or change phase deadlines/IDs. Runtime blocking inside the pose query was not measured directly.

## Memory cleanup candidate, separate from the observed freeze mechanism

Static analysis found a stock `FlipFrame` error-path cleanup gap in both 5002322 and 5002363. Metadata/import failures can return without releasing every EGLImage/AImage resource. The exact 4 triggering error strings occurred **0 times** in the main live capture. The later FEC metadata messages are different errors at a different stage.

This is a concrete conditional defect to investigate separately, not an observed explanation for these freezes. No speculative APK/native fix was applied. See [exact offsets and control flow](native-leak-candidate.md).

## Limits and observer effects

- The first detailed `dumpsys meminfo` sampling caused or coincided with explicit app GC/object enumeration about every 10 seconds: 32 explicit GC log messages, 9 during the 90-second trace. Its longest observed object-enumeration suspension was about 18 ms. Later captures and the bandwidth comparison use `--local`, avoiding the app RPC; the collector now defaults to that mode.
- Resets were already present before this collector, and continued in the later light capture. They are not explained solely by the memory sampling.
- Perfetto reports 38 out-of-order sorter events, 23,469 systrace parse failures, and 4 lost trace packet sequences. Do not interpret absent trace events as proof that a subsystem never stalled.
- Full-space XR video did not appear as useful Android SurfaceFlinger app frame-timeline records. Decoder output gaps do not prove that the physical panel or reprojection stopped.
- No app runnable or uninterruptible-blocked interval >10 ms was observed in available scheduler records. This does not exclude logical waits, lost trace events, or delays elsewhere in the pipeline.
- Android thermal service reported status 3 throughout the sampled baseline. Android defines this as severe thermal mitigation; virtual sensor readings are not physical CPU/GPU temperatures. Thermal contribution was not isolated. [Android thermal documentation](https://source.android.com/docs/core/power/thermal-mitigation)
- Strong Wi-Fi signal and zero host Ethernet errors do not exclude Wi-Fi delivery jitter. Lowering bandwidth and changing encoder workload also cannot isolate the radio alone.
- Host/device wall clocks differed by about 0.45 seconds. Correlation accounts for the measured offset with roughly 0.06-second uncertainty; close cross-device ordering remains uncertain.
- The steady `Buffer item consumer returned null buffer` log appeared about 90 times/second, including healthy intervals. Its volume alone is not evidence that it triggers the freezes.

## Next discriminating investigation

Capture the same pose-cycle ID at **generation, scheduled dispatch, socket send, and host receive**, with monotonic timestamps in bounded buffers. The first stage where an old ID overtakes a new one distinguishes client deadline bunching from transport/receive reordering. Include elapsed time inside the OpenXR pose query. Current logs do not expose all these points.

A separately authorized comparison with the active custom NVENC hook disabled would isolate another concrete variable, but requires a driver/session change. It was not part of the approved bitrate-only comparison. The stock cleanup defect should be validated separately using its exact error branch and image-resource ownership; it should not be promoted to a freeze fix from the present evidence.
