# Profile photos and current post-image clipboard

The `saveProfilePhoto` action follows the frozen iOS reference's 300 ms hold, 1024-pixel image request, and Save/Copy choices. Android saves a PNG through MediaStore and copies a read-only PNG content URI through the existing `LongPressImageProvider`. It uses the native image source, including its crop options, rather than taking a screenshot of the circular avatar view. No action is available while the native request still shows a placeholder or has failed.

The original Morphe 2.0.0 post-image feature deliberately excludes avatar-sized images. Its existing post/GIF save behavior remains intact. The additional post-sheet **Copy current image** action reuses Morphe's original post identity and visible-carousel-image resolver; it does not introduce another post parser or download UI.

## Native avatar ownership

`avatarPhotoHookPatch` validates these YouTube 21.43.523 boundaries before injecting:

- `Lwsp.L(Lhfs;Object;Lhhw;)V` passes its actual `ImageView`, the selected `Lwsy.b:Lwev` image source and its `Lwuw` conversion context into the 20-argument `Lwsu` constructor. `Lwev.q()` identifies a remote URL source and `Lwev.k()` returns that URL.
- `Lwsu` inherits `Lhar`/`Lhaw`; the original `Lhaw.a:View` field is the image target. A generated no-argument method reads that field, the stored source/context and `Lwuw.b:WeakReference`. The constructor invokes it only after native initialization. The patch verifies that the original constructor never overwrites its receiver and has one return.
- The sole `Lhar.b(Object,Lhbd)` super call inside `Lwsu.b(Object,Lhbd)` is the successful resource-ready callback. Only this callback enables the current binding. A callback belonging to a recycled target cannot enable a newer binding.
- `Lwsp.as(Lhfs;Object)` clears the exact binding at native unmount. Its original request-clearing and drawable-clearing behavior remains unchanged.
- The leaf must be exactly `avatar.eml-fe|<16 hex digits>|ImageType|`. Build124's cached component logs demonstrate this leaf on the watch channel bar, feed cards, comment teasers, Shorts channel avatars, actual comments and post headers. Other image/component paths are rejected.

The runtime checks a native root token when the context provides one, the current main Activity view tree, attachment, visibility, drawable availability and the touched visible image rectangle. Build128 runtime counters proved that the watch renderer often supplies no `Lwuw.b` token despite the exact avatar path/source and successful native image callback. In that case the already identified image target and its native mount/unmount lifecycle own the action. A cleared or mismatched token is still rejected when one was supplied. A detach listener also clears the binding, so attachment or a late callback cannot revive an old target without a new native bind.

Ancestor walking only validates these already identified owners. It does not classify arbitrary images or text. Ordinary taps and installed native click/long-click listeners remain in place. A successful hold opens the sheet before sending native touch cancellation; scrolls, multi-touch, unmount and recycled identity cancel pending holds. `claimsTouch` gives this exact avatar target priority over the containing comment/post screenshot gesture.

## Original Morphe selection reuse

`longPressPostImageHookPatch` adds one accessor to the pinned `PostImageDownloadPatch` runtime. It calls the original `findPostKey(root)`, `getImages(key)` and `getShownImages(root, images)`, returning the post key and existing `PostImage.shownUrl()` only when exactly one image is returned. The accessor retains the original `ENABLED` gate. Its dependency on the common extension only makes the existing runtime class available: it does **not** select `Download post images`, change `isPatchIncluded`, change its preference or install its element hook.

`LongPressPostImageActions.copyAction(Activity, View)` receives the exact post root already established by `LongPressCaptureTools`. Missing or ambiguous original results add no row to the sheet. The returned action owns a key/URL snapshot and resolves the same root again at activation. A changed post, changed selected slide, detached root, disabled owner or replaced Activity prevents copying the old image. Original Morphe saves retain their original format/GIF support; clipboard copying produces a static PNG.

Both image actions reuse `AvatarPhotoSource` for HTTPS requests. The loader accepts the verified Google image hosts, preserves native URL options except the explicit `=sNN` size, applies the existing `fixAlbums` host override, follows at most four allowed redirects and limits input to 8 MiB. It does not add authentication or cookie headers. Decoding rejects invalid or oversized dimensions and samples the result to at most 2048 pixels on its longest side. URLs and image data stay in memory until the provider writes the user-requested output; diagnostic messages contain no URL, post key or image content.

## Validation and remaining runtime checks

`python3 tools/check_avatar_photos.py` passes 56 identity/URL/HTTP-transfer checks, 62 production avatar binding/gesture checks and 38 production post-image snapshot checks. The tests cover absent optional root tokens, stale native callbacks, detach/unmount/recycling, root replacement, ambiguous image hit areas, scrolling and short taps, parent/child dispatch, disabled owners/preferences, partial/oversized responses and unsafe redirects. They also verify that opt-in stage diagnostics contain no image URLs or component paths and stop after 64 lines per process. The changed runtime compiles against the actual build128 extension classes and Android 36. The earlier stock-APK/pinned-Morphe audit passed 43 native descriptor/access/inline-smali assertions; an actual build127 APK audit also confirmed all 26 relevant avatar lifecycle and dispatch instructions. Source and native audit evidence is in `~/.cache/ytafterglow-android/afterglow-vault-20261116/avatar-photo/`.

Build129 runtime verified the watch-avatar hold, Save and Copy paths. Holding the freeCodeCamp watch avatar opened the Profile photo sheet with Save, Copy and Cancel; Save produced the correct logo as a decodable 1024 × 1024 PNG, 156,549 bytes, SHA-256 `d596327f3eaf3da9643716c68c923e91032b4f6dd1698adb067894fd02caa098`. With emulator host clipboard synchronization disabled, a separate foreground app read the copied content URI as `image/png`, labeled `Afterglow image`, and decoded exactly the same dimensions, bytes and SHA-256. An ordinary short tap still opened the native freeCodeCamp channel. Evidence is in `~/.cache/ytafterglow-android/afterglow-vault-20261116/bundle-129-qa/native-runtime/`, including `003-avatar-fixed-hold.png`, `avatar-saved.png`, `avatar-clipboard-isolated-report.json`, capture016 and `018-avatar-short-tap-native-channel.xml`.

The initial cross-app Copy check encountered an emulator QA environment issue: host synchronization overwrote the image clip. The foreground probe's `avatar-clipboard-source-report.json` reports the label `host clipboard`, MIME `text/plain` and empty text, instead of the provider's `Afterglow image` URI clip. The [Android 16 emulator clipboard bridge](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/services/core/java/com/android/server/clipboard/EmulatorClipboardMonitor.java) converts URI-only clips to empty host text and writes incoming host text with that label. Disabling that synchronization for the repeat established successful cross-app PNG access without changing production clipboard behavior.
